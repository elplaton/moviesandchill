# AGENTS.md

## Quick start

```bash
cp .env.example .env   # edit with real TMD_API_ID, TMD_API_HASH, TMD_PHONE
docker compose up -d   # db → backend → frontend (port 80)
```

First login requires interactive Telegram auth. If `session/user.session` doesn't exist:
```bash
cd backend && source ../venv/bin/activate && python main.py setup
```
Then `docker compose restart backend`.

**Dev mode** (no Docker, backend on :8000, frontend on :5173 with proxy):
```bash
# Terminal 1
cd backend && uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
# Terminal 2
cd frontend && npm run dev
```

## Architecture

```
Browser :80 → nginx (frontend) → proxy /api/* → :8000 (FastAPI backend)
              ├─ /      web de escritorio (frontend/)
              ├─ /m/    PWA de móvil (mobile/), redirigida desde / en teléfonos
              ├─ /tv/   app de TV (tizen/src) que cargan Samsung y Fire TV
                        al arrancar, para actualizarse solas
              ├─ /tv-webos/ la misma para el paquete de LG, que además
                        funciona en webOS 4 (Chromium 53)
              └─ /ps4/  la misma app compilada para el navegador de la
                        PlayStation, redirigida desde / en la consola
                                                    ↓
                                              PostgreSQL :5432
                                              Redis :6379  (caché, opcional)
                                              Telegram API
                                              TMDB API
```

- **frontend**: React 18 + Vite 5 + Tailwind 3. SPA served by nginx. La imagen se construye desde la raíz del repo (`context: .`) e incluye también `mobile/` en `/m/`. Interfaz pensada para ratón y teclado: `Shell` (barra + contenido + `ActivityDock`), `TopBar` con buscador («/» lo abre), `Hero` de portada, `Rail` (carril con flechas, porque en escritorio no hay swipe), `Card` (carátula limpia, acciones al pasar el ratón), `TitleSheet` (ficha ancha única para película y serie) y `Player` (controles propios: espacio, ← →, ↑ ↓, F, M, Esc). Tokens en `tailwind.config.js` (paleta `nf-*`, escala tipográfica, `--gutter`).
- **mobile**: PWA (React + Vite + Tailwind, `base: /m/`), manifest + service worker en `public/`. Pensada para el teléfono: armazón fijo con `<main>` desplazable (la barra de pestañas no se mueve con la de Safari), ficha por ruta (`/m/t/:kind/:tmdbId`), `<video>` nativo que entra en pantalla completa al arrancar y se cierra al salir de ella. **Se actualiza sola**: `scripts/stamp-sw.mjs` marca `dist/sw.js` con la fecha del build; el SW hace `skipWaiting`+`claim` y `main.tsx` recarga una vez en `controllerchange`. Dev Vite proxy sends `/api`→`:8000`, `/ws`→`ws://localhost:8000`.
- **backend**: Python 3.12 + FastAPI + Telethon. Split into `app/routers/*`, `app/services/*`, `app/database/*`; `app/routers/download.py` is now just the wiring (`init_download_router`). Session file at `session/user.session` (gitignored — never commit it). Downloads go `downloads/` → extract → `movies/`.
- **db**: PostgreSQL 16-alpine. Tables auto-created on startup. No migration framework.
- **cache**: Redis 7-alpine, sin persistencia y con `maxmemory-policy allkeys-lru`. Es **opcional**: sin `TMD_REDIS_URL` la aplicación funciona igual, solo recalcula la portada y las fichas en cada visita. Lo que guarda y quién lo invalida está en `backend/app/services/cache.py`.

## Config

Everything via `.env` with `TMD_` prefix. `.env` search order: cwd → parent of `app/config.py` → dotenv default.

**Critical vars**: `TMD_API_ID`, `TMD_API_HASH`, `TMD_PHONE`, `TMD_JWT_SECRET`, `TMD_DATABASE_URL`, `TMD_TMBD_API_KEY` (note: TMBD typo, not TMDB).

`TMD_JWT_SECRET` es **obligatorio**: el arranque aborta si falta, es uno de los valores de ejemplo, o mide menos de 16 caracteres. Antes había un fallback (`default-secret-change-me`) que permitía a cualquiera firmarse un token de admin.

`TMD_REDIS_URL` enciende la **caché**. Vacío = sin caché: todo funciona igual,
solo se recalcula en cada visita. En casa lo pone el propio `docker-compose.yml`
(servicio `cache`); en Coolify es un recurso aparte (ver `DEPLOY-COOLIFY.md`).

`TMD_ANTHROPIC_API_KEY` es la clave de la API de Anthropic para la **revisión con IA** (`services/revision_ia.py`). Vacía = no se usa. El gasto del mes (y el tope) es lo que ha costado de verdad cada petición, sacado de su `usage`: lo del servidor y las pruebas hechas desde fuera con la misma cuenta, que se apuntan con `revision_ia.apuntar_prueba()` y salen en el historial como «prueba». Lo que la cuenta gaste por otro lado no se ve: Anthropic solo se lo dice a una clave de administrador, y se decidió no tener otra clave. Va en el `.env` (en Coolify, en las variables del recurso, y la nombra `docker-compose.coolify.yml`) y no en el panel, a propósito: es un secreto.

`TMD_PUBLIC_URL` es la dirección por la que se entra desde el móvil (en Coolify, `https://moviesandchill.juanitoshomelab.com`, que ya viene por defecto en `docker-compose.coolify.yml`): es a donde lleva el QR con el que se entra en la tele. Vacío = la dirección por la que llegue la petición.

`TMD_CREDITOS` (encendido por defecto) es el interruptor general de los créditos, «Usar los créditos» en la pestaña **Créditos** del panel: apagado, `/api/creditos` contesta como si no se supieran, así que los cuatro clientes vuelven a sacar la tarjeta del siguiente (y a dar por visto) 45 s antes del final, y no se mide nada al ver; lo medido no se borra y la pasada completa sigue con su propio botón. `TMD_CREDITOS_ANALIZAR` (apagado por defecto) deja que el servidor averigüe los créditos mirando la imagen al reproducir algo que no los tiene (ver `services/proceso_creditos.py`); gasta Telegram, así que hasta encenderlo solo se usan los capítulos de créditos de los archivos y lo ya medido. Se enciende también desde la pestaña **Créditos** del panel («Averiguar los créditos al ver», junto a la pasada completa y lo que ya se sabe), y eso se guarda en `app_settings` y manda sobre el `.env` (`SAVED_BOOL_KEYS` en `config.py`). `TMD_INTERIOR_VIGILANTE` (apagado por defecto) deja que el servidor mire por su cuenta qué rar, 7z y zip guardan el vídeo tal cual (ver `services/interior.py`); apagado, el «Ver» de los comprimidos funciona con lo que ya esté en la tabla `interior`. Otras vars: `TMD_DOWNLOAD_CONEXIONES` (conexiones a Telegram por archivo, 6 por defecto, 1 = como antes), `TMD_AVISOS_MINUTOS` (cada cuánto se mira si han llegado episodios de las series seguidas, 10 por defecto, 0 desactiva), `TMD_PUSH_CONTACT` (el correo que va en la firma de los avisos), `TMD_RESCAN_HOURS` (barrido incremental cada N horas, 6 por defecto, 0 desactiva), `TMD_STATE_DIR` (dónde vive `paused_batches.json`), `TMD_CORS_ORIGINS` (coma-separado; con `*` se desactivan las credenciales), `TMD_ADMIN_PASSWORD`, `TMD_LOG_UNIT`.

Booleans: `"1"`, `"true"`, `"yes"`, `"s"`, `"si"` → true. Spanish-friendly.

Default admin: `admin`/`admin` (o `TMD_ADMIN_PASSWORD`). Se crea al arrancar con PBKDF2-HMAC-SHA256 (240k iteraciones). Los hashes antiguos en formato `salt$sha256` se siguen aceptando y se migran a PBKDF2 en el primer login.

## Gotchas

- **Session path**: `_session_path()` searches cwd, then package root, then falls back to `cwd/session/`. Docker mounts `./session:/app/session`. CLSetup sets `session_dir` explicitly to `../session/` (project root). Both must agree.
- **Channel IDs**: stored as positive in DB (`entity.id`), but Telethon needs `-100XXXXXXXXXX`. `_resolve_channel_id()` adds prefix.
- **Multi-part archives**: detected by `storage.py` regex (`\.partN\.rar`, `\.rNN`, `\.7z\.NNN`, `\.\d{3,}$`). Backend's `find_related_parts()` searches all channels for matching base name.
- **Frontend grouping**: `groupSearchResults()` en `utils/search.ts` (web, móvil y tizen) agrupa resultados de búsqueda por `tmdb_id` si lo hay, y si no por el nombre de serie que va delante del `1x01`. 
- **Detalle por tmdb_id**: los modales de película/serie cargan `GET /api/media/{tmdb_id}/files`, nunca `/api/search` con el título. Con `ILIKE` del título en español de TMDB, 2 de cada 3 series salían sin episodios ("Cómo conocí a vuestra madre" vs "How I Met Your Mother 1x01").
- **Clasificación película/serie**: la decide `title_parser.parse_filename()` (`1x01`, `S01E01`, `T01E10`, `[S05.E06]`, `Temporada N`, `episodio N`, `Nombre - 89`, `Nombre_149_...`). El texto que se manda a TMDB es solo el nombre de la serie (lo de delante del marcador), no el título del episodio; antes "Suits La vida útil" emparejaba con la película "La vida me sienta bien". `tmdb_valid` = tipo detectado == tipo TMDB y **solo lo válido sale en la Home**. Tras cambiar el parser: `POST /api/index/reclassify` (botón "Reclasificar catálogo" en Canales) re-parsea y re-busca lo que estaba sin emparejar o con el tipo equivocado.
- **La velocidad de descarga la calcula el servidor, no el cliente**. El cliente la sacaba **deshaciendo el texto** de lo descargado (`"1.2 GB"` → bytes) y restando contra la medida anterior; a escala de GB `format_size` tiene una resolución de 100 MB, así que con muestras de un segundo el número salía a saltos o en blanco. Los bytes exactos los tiene el servidor: `batch_progress` (y `/status`, para el móvil, que suspende el WebSocket al apagar la pantalla) llevan ahora `downloaded_size`, `speed`, `speed_str` y `eta_str`, y la interfaz pone «1,2 GB de 4,5 GB · 8,3 MB/s · faltan 6 min». Dos cuidados. La velocidad se **suaviza** (media exponencial con peso 0,8 a lo anterior) porque Telegram manda a ráfagas: medido sobre ráfagas simuladas, sin suavizar el número daba saltos de 7 MB/s entre segundos consecutivos y con esto de 2, sin que la media deje de ser la real. Y **caduca**: si no llegan bytes el callback no se llama y el valor se queda congelado, así que `/status` lo da por 0 pasados 6 segundos en vez de mentir. El dato se guarda en el lote y no en cada parte: las partes bajan de tres en tres y lo que se quiere saber es la velocidad del conjunto.
- **"Descargar" en el modal**: el número que antes salía entre paréntesis eran *partes* del mismo archivo comprimido, no opciones; al pulsar se bajan todas las partes y se extraen. Ahora el botón dice solo "Descargar" y la fila muestra "N partes · tamaño".
- **Conversión de compatibilidad**: `_make_compatible()` en `download_router.py` detecta códecs vía `mediainfo` y transcodifica a H.264/AAC/MKV. Corre en executor (bloqueante). Escribe a un temporal y solo reemplaza si acaba bien. Ojo: `_info()` devuelve `""` si `mediainfo` no está instalado, y una cadena vacía se interpreta como "compatible" (no se convierte).
- **TMDB enrichment**: corre en un único bucle en paralelo al escaneo (`ensure_enrich_worker()`, guardado por `_enrich_running`), no dentro de cada lote: con 250k mensajes esperar a TMDB por lote suponía horas. Concurrencia 10 (`TMDB_CONCURRENCY`), 300 items/batch, agrupando por título (una consulta por serie, no por episodio). El bucle sigue vivo mientras `_active_scans > 0`. `get_media_without_tmdb()` solo devuelve `tmdb_searched = FALSE`: antes re-preguntaba a TMDB por los 11.000 sin resultado en cada pasada.
- **Ids de TMDB**: películas y series tienen espacios de ids **independientes** (`tv/606` = Ed, Edd y Eddy; `movie/606` = Memorias de África). `tmdb_cache` tiene clave `(tmdb_id, media_type)` y `media_items.tmdb_type` guarda el tipo; **todo JOIN con `tmdb_cache` debe ir por las dos columnas**. `GET /api/media/{id}/files?media_type=tv|movie` exige el tipo. Con la clave antigua cada ficha pisaba a la otra y aparecían películas con "199 episodios".
- **El buscador compara títulos normalizados, no el texto tal cual** (`services/busqueda.py`). Era `ILIKE '%texto%'` y fallaba con lo normal: «MAY DAY» no encontraba «Mayday», «x men» no encontraba «X-Men» y sin tildes no salía «Cómo conocí…». Ahora el título y lo buscado pasan por lo mismo —minúsculas, sin tildes, sin signos, con las palabras separadas (`busca`) o pegadas (`busca_c`)— y coincide si es igual, si empieza así, si tiene todas las palabras buscadas al principio de alguna suya (en cualquier orden) o, con cuatro letras o más, si lo buscado está dentro. Los resultados salen **por ese orden** y, a igualdad, lo más votado en TMDB primero: antes iban por `tmdb_id` y la película buscada podía salir detrás de otras. Las columnas normalizadas son `GENERATED ... STORED` en `media_items` (de `clean_title`) y `tmdb_cache` (de `title` y `original_title`), así que no hay que rellenarlas al insertar; la expresión la da `expr_sql()` y `normalizar()` hace lo mismo en Python (lo comprueba `prueba_busqueda.py`). Ojo: una columna `GENERATED` no admite valor en un `INSERT`, así que las inserciones tienen que seguir nombrando sus columnas. Si la consulta nueva falla, `search_media` lo registra y vuelve al `ILIKE` de antes. **Lo que traía cosas sin relación era sobre todo Telegram**: con `page_size` 100 una película concreta nunca llenaba la página, así que siempre se completaba con su búsqueda en vivo, que es muy laxa; ahora solo entra lo que `coincide()` con lo buscado.
- **Search fallback**: `/api/search` consulta PostgreSQL primero. Ojo con los dos offsets: `offset` son filas a saltar en SQL y `offset_id` es un ID de mensaje de Telegram — no son intercambiables. If < page_size results, falls back to live Telegram search. Deduplicates by `(channel_id, message_id)`. Enriches Telegram results with TMDB metadata on-the-fly.
- **Entradas de reproducción (`type: "stream"`)**: la URL del vídeo lleva el token dentro y la lee alguien que **no puede renovarlo** — el propio `<video>`, o un Apple TV por AirPlay. Con el token de acceso (60 min) cualquier película más larga que eso se cortaba a mitad con un 401, y en AirPlay sin remedio. `create_stream_token()` emite un permiso de 12 h pero **limitado a una ruta**; `get_stream_user()` lo acepta en `/api/stream` y `/api/subtitle` además del token normal, y `_cubre()` deja que la entrada de un vídeo sirva también para sus `.vtt` de al lado (son ficheros distintos y pedir una entrada por pista sería una vuelta más al servidor). Los clientes la piden con `streamTicket(path)` al abrir el reproductor y, si falla, caen al token de acceso: peor para una peli larga, mejor que no reproducir.
- **AirPlay** (`hooks/useAirplay.ts` en web y móvil): es API propia de WebKit (`webkitShowPlaybackTargetPicker`), así que el botón solo sale cuando WebKit avisa de que hay algún dispositivo al alcance — no vale mirar el *user agent*, porque sin Apple TV en la red el selector saldría vacío. En el móvil el reproductor del sistema ya trae el suyo dentro de la pantalla completa; el botón propio está en la pantalla de espera para poder mandarlo a la tele **antes** de empezar, y si AirPlay está activo no se entra en pantalla completa (solo se vería el cartel de AirPlay). **Los subtítulos no viajan**: en AirPlay el receptor descarga la URL del vídeo él mismo y los `<track>` los pinta el navegador, que se queda aquí.
- **Streaming**: `/api/stream` tiene semáforo (máx. `TMD_STREAM_MAX`, 3 por defecto). La plaza se pide **dentro del generador** y se suelta en su `finally`, así que cogerla y devolverla son el mismo trozo de código. Pidiéndola en la vista quedaba un hueco entre el `acquire` y el primer tramo enviado: si el cliente se iba justo ahí el generador no arrancaba, su `finally` no corría y **la plaza se quedaba cogida para siempre** — y un `<video>` de iPhone abre y cancela rangos sin parar (al buscar, al llenar su buffer, al volver de segundo plano), así que tres cancelaciones con suerte dejaban la siguiente reproducción esperando sin recibir un byte y sin nada en los logs. El límite es además **blando**: si no hay plaza en `ESPERA_PLAZA` (10 s) se sirve igualmente con un `WARNING`, porque está para no reventar el disco con diez reproducciones, no para dejar a nadie ante una pantalla negra. Lectura con `aiofiles` para no bloquear el event loop.
- **Cuánto adelanta el vídeo no se configura**: en iOS lo decide el reproductor del sistema según la velocidad que mida; `preload="auto"` es lo único que se le puede pedir y no es una orden. Un `<video src=…>` baja el archivo tal cual, así que **si el archivo pide más Mbps de los que da la red, va a tirones** y no hay ajuste del servidor que lo arregle (eso sería HLS con varias calidades, que no hay). Ante un tirón, el número que hay que mirar es el bitrate: `GET /api/media/tracks` lo devuelve (`bitrate`, `duration`, `size`; en MKV ffprobe no siempre trae `bit_rate`, y entonces sale de tamaño/duración) y se compara con lo que da el enlace (`curl -r 0-104857600 -w '%{speed_download}'` contra `/api/stream`). Ojo también con lo de al lado: una conversión o una extracción en marcha satura CPU y disco, y eso se nota como tirones aunque la red vaya sobrada.
- **El stream lo lee un cliente más estricto que Safari**. Por AirPlay el receptor (Apple TV, o la tele) **se descarga la URL él mismo** con AVFoundation, y ahí se vio que faltaban dos cosas que el navegador nunca pide: `/api/stream` solo aceptaba `GET`, así que el **`HEAD`** con el que AVFoundation empieza a sondear devolvía un **405** — daba el vídeo por un directo no navegable y se quedaba sin obedecer pausa, play ni búsqueda —, y el regex del `Range` solo entendía `bytes=N-M`: **`bytes=-N`** (los últimos N bytes) no encajaba y se servía el archivo entero desde el byte 0, pero con un 206 y un `Content-Range` que lo daba por bueno, así que quien pedía la cola recibía la cabeza sin enterarse. El síntoma era **la película se oía pero no se veía**. Ahora se responde al `HEAD` (con `Content-Length` y `Accept-Ranges`, y **antes del semáforo**: un sondeo no debe gastar plaza de reproducción), se admiten las tres formas de `Range` y lo que no se puede servir es un **416 con `Content-Range: bytes */<tamaño>`** en vez de una respuesta que miente. Ojo al diagnosticar esto: el archivo puede estar perfecto (se comprobó el códec, el `moov` delante y las banderas del `tkhd`) y el fallo estar en las cabeceras.
- **`Connection: upgrade` solo para el WebSocket**: `frontend/nginx.conf` lo mandaba en **todas** las peticiones de `/api/`, aunque no hubiera `Upgrade`. Con eso un GET normal llega al backend con una combinación de cabeceras inválida y la conexión no se reutiliza: cada tramo de vídeo abre un TCP nuevo (y un *handshake* TLS si viene de fuera), y un `<video>` pide muchos tramos. Va por el `map $http_upgrade $conexion_upgrade` de siempre (`'' → close`), que es lo que deja vivo `/api/ws/progress` sin cobrárselo al resto.
- **WebSocket progress**: broadcasts como mucho 1/seg. El token va en `?token=` y **se valida**: sin token válido se cierra con código 1008. Reconecta cada 5s.
- **Logs endpoint**: `GET /api/logs` (solo admin: lleva nombres de cuenta y rutas) llama a `journalctl -u $TMD_LOG_UNIT` (por defecto `telegram-movie`) bajo systemd; en Docker, que es como corre en Coolify, devuelve las últimas 3.000 líneas que el propio servidor guarda en memoria (`services/registro.py`). Antes ahí solo había un error y Admin → Registros salía vacío.
- **Spanish**: all user-facing strings, CLI output, API messages, and logs are in Spanish. Code identifiers mixed Spanish/English. API JSON keys in English.
- **`TMD_TMBD_API_KEY`**: intentional typo in env var name. Both code and .env.example use this spelling.
- **Estructura en disco** (`services/layout.py`): series → `<extract>/<Serie>/Temporada N/<N>x<EE>.<ext>`; películas → `<extract>/<Título (Año)>/<Título (Año)>.<ext>`. Los nombres salen de TMDB (`get_media_item()` sobre el catálogo) y, si no hay, del parser. Cada lote baja a una carpeta temporal `.dl_<batch>` dentro de su destino, se extrae/convierte ahí y `finalize_episode()` mueve el vídeo con su nombre final y borra la temporal; al cancelar/fallar se borra y se podan carpetas vacías (`prune_empty_dirs`). `/files` entiende esta estructura y la antigua (`Serie S1/`). Cada parte lleva su `channel_id` y `download_to_folder()` lo usa: **el `message_id` se repite entre canales** y sin él se descargaba el archivo de otro canal.
- **Extraction**: sync/blocking via `run_in_executor`. Auto-flattens single-subfolder nesting (`movies/Name/Name/video.mkv` → `movies/Name/video.mkv`).
- **paused_batches.json**: gitignored. Vive en `TMD_STATE_DIR` (montado como `./state` en Docker) en vez de ser relativo al cwd. Pausar borra **solo** las partes incompletas: las ya descargadas deben sobrevivir o el "reanudar" no sirve de nada.
- **Pausar y reanudar comparten `batch_id`, y eso tenía tres agujeros**. (1) La tarea pausada sigue viva 10 s tras pausar y al acabar quitaba de `active_batches` y `_batch_tasks` **lo que hubiera con su id**, que si se había reanudado enseguida era ya la reanudación: seguía bajando sin salir en Descargas, sin poder pausarse ni cancelarse y sin que `iniciar_descarga` la viera, así que «Descargar» lanzaba **otra** encima en la misma carpeta. Ahora las dos limpiezas comprueban que lo que quitan es suyo (`_lanzar()`). (2) `/pause` contestaba antes de que la tarea borrase su parte a medias, y un «Reanudar» rápido empezaba a escribir el archivo justo cuando la limpieza lo borraba; ahora espera a esa limpieza. (3) «Descargar» sobre algo en pausa lanzaba una descarga nueva y la pausa seguía ofreciendo «Reanudar»; ahora **reanuda**. Además una pausa se puede **descartar** (`/cancel` sobre un lote pausado), porque cuenta en la cuota y antes la única salida era reanudarla, y al arrancar se descarta una fila `paused` cuyo lote ya no está en `paused_batches.json`. Probado en `backend/tests/prueba_pausa.py`.
- **Un archivo a medias no es un archivo descargado**. `download_to_folder()` daba por bajado cualquier archivo que pesara algo, y un doble clic en «Descargar» (el primero aún esperando a Telegram) arrancaba dos tareas del mismo lote: la segunda encontraba lo que estaba escribiendo la primera y **a los tres segundos dejaba en la biblioteca una película cortada** (pasó con «El diablo viste de Prada 2»). Ahora solo cuenta si mide lo que dice Telegram, e `iniciar_descarga` aparta el lote mientras se prepara (`_preparando`), así que el segundo clic contesta «Ya se está preparando».
- **La velocidad de descarga no la ponía la cuenta, la ponía el código**. Se pagó Telegram Premium y no cambió nada, y tenía que ser así: `download_media()` pide el archivo en trozos de 512 KB **de uno en uno** (pide, espera, descifra, escribe, y solo entonces el siguiente), así que el tope es 512 KB por ida y vuelta —unos 5 MB/s con 100 ms— y el límite que Premium quita ya no era el que mandaba. Además la imagen no llevaba **`cryptg`**: sin él Telethon descifra con la libssl del sistema si la encuentra y, si no, **en Python puro, a menos de 1 MB/s** (medido) y bloqueando el bucle de eventos. Ahora `cryptg` va en `requirements.txt` y `services/descarga_paralela.py` abre **varias conexiones por archivo** (`TMD_DOWNLOAD_CONEXIONES`, 6), cada una pidiendo trozos alternos y escribiéndolos en su sitio, que es lo que hacen la app de escritorio de Telegram y FastTelethon. Cuatro detalles. Son **conexiones distintas** (`MTProtoSender` propios) y no peticiones en paralelo por la principal: ahí se encolan detrás de las respuestas de 512 KB de las otras y además frenarían la indexación. Si el archivo vive en otro DC, la primera exporta la autorización y el resto reusa esa clave (exportar una por conexión es un segundo de más cada una). Usa piezas **internas** de Telethon 1.x (por eso `telethon<2`), así que si algo falla antes del primer byte se lanza `SinParalelo` y se baja con `download_media()` como antes. Y se baja a **`<nombre>.parcial`** y solo se renombra al acabar: en paralelo el último trozo puede escribirse antes que los del medio, y un archivo que mide lo que debe sin estar entero es justo lo que la comprobación de «ya descargado» no sabe distinguir (la pausa borra también el `.parcial`). Para saber qué está pasando: el log de arranque dice Premium, motor de cifrado y conexiones; cada archivo deja una línea con sus MB/s; y la pestaña **Telegram** del panel enseña lo mismo. No hace falta cerrar sesión para que Premium cuente: Telegram lo aplica a la cuenta, no a la sesión. **Medido después en el servidor**: con la cuenta Premium y `cryptg`, 6 conexiones daban 5,3 MB/s clavados con la CPU al 15 %, el disco parado y una línea de 620 Mb/s; en el log había **4.204 esperas forzosas** (`flood wait` de 1-2 s en `GetFileRequest`) en una sola película. Se probó a pedir trozos de **1 MB** (el máximo que admite `upload.getFile`; si un DC lo rechaza con `LIMIT_INVALID` se vuelve a 512 KB) por si Telegram contaba peticiones, y la velocidad siguió igual: lo que limita es el **ancho de banda de la cuenta, ~5,3 MB/s**, repartido entre todas las conexiones y todas las partes (una descarga de 3 partes sumaba lo mismo). Las esperas las gestiona `descarga_paralela`, mandando las peticiones directamente por cada `MTProtoSender` (`sender.send`) y no por `client._call`, que las duerme él solo **e ignora el `flood_sleep_threshold` que se le pasa** (mira solo el del cliente); así la línea «Descargado …» dice cuántas hubo y de qué tipo: `FLOOD_PREMIUM_WAIT` es el freno a las cuentas sin Premium y `FLOOD_WAIT` un límite general. Telethon registra los dos con el mismo mensaje, así que sin esto no se distinguen. Probado en `backend/tests/prueba_descarga_paralela.py`.
- **Ver sin descargar (`services/reproduccion.py`)**. Es lo que hace Telegram Desktop al reproducir sin bajar: pedir los trozos del archivo (`upload.getFile`, lo mismo que una descarga) en el orden en que los necesita el reproductor. Aquí el reproductor es el `<video>` de cada cliente pidiendo tramos a **`/api/stream`, que con una ruta `tg:<canal>:<mensaje>` los saca de Telegram en vez del disco**; por eso los tres reproductores, la entrada de reproducción, `/media/tracks` y el progreso no han necesitado cambios: para ellos es una `path` más (en `playback_progress` se guarda tal cual y `continuar.py` no la descarta por no estar en disco). Qué se puede ver se decide **antes de pulsar nada** (`streamable` en cada resultado), para que «Ver» nunca acabe en «estaba comprimido»: vídeo suelto o partes sin comprimir como `Peli.mkv.001` por la extensión, y un zip, rar o 7z solo si ya se ha mirado por dentro y guarda el vídeo tal cual (ver «Comprimidos que se ven» más abajo). Después `GET /api/reproducir`, que lo confirma leyendo unos KB y pasando **ffprobe sobre el propio stream** (con una entrada de reproducción del usuario `sistema`) y lo guarda en la tabla `reproduccion`: un mensaje no cambia de contenido, así que se mira una vez; lo pasajero (Telegram desconectado, una parte que aún no está indexada) no se guarda. Tres cosas que sostienen esto. **Las partes se sirven como un solo archivo**: cada tramo pedido se reparte entre los mensajes que toque. Si en algún aparato «Ver» no puede, la ficha dice el motivo con un botón «Descargar» al lado. **El iPhone es el más estricto**: solo MP4/MOV con vídeo que entienda y audio AAC, lo que al descargar arregla `make_compatible()`; el móvil lo mira con lo que devuelve ffprobe (`motivoNoSeVe()`) y si no se puede lo dice en vez de abrir un vídeo mudo o negro. Adaptar al vuelo (MKV o AC-3 en el iPhone) es la fase siguiente. Comparte con las descargas el límite de ancho de banda de la cuenta de Telegram. Probado en `backend/tests/prueba_reproduccion.py`.
- **Comprimidos que se ven sin descargar (`services/interior.py`)**. Un rar, 7z o zip en modo «almacenar» guarda el vídeo byte a byte y solo lo trocea, así que se puede servir desde Telegram como unas partes `.mkv.001`: basta saber **en qué tramo de qué mensaje** está. Medido en noviembre de 2026 sobre dos muestras de 300 de lo que solo se podía descargar: lo es un **14 %** (un 8 % de las películas, casi la mitad de los episodios); **K9 Películas lo comprime todo** (7z LZMA), y para lo comprimido de verdad no hay atajo: alguien tiene que bajarlo. Que va almacenado lo dice la cabecera y no el nombre, así que un vigilante (`vigilante()`, al arrancar y cada 30 min, **solo con `TMD_INTERIOR_VIGILANTE`**, apagado por defecto: la primera revisión se hizo desde el Mac con la sesión de pruebas y se cargó en la tabla) lee la del primer volumen de cada comprimido del catálogo —primero los títulos sin ningún enlace que se pueda ver— y lo guarda en la tabla **`interior`** (clave el primer volumen; `volumenes` los lleva todos, porque la ficha pinta «Ver» en cada parte y el reproductor puede pedir cualquiera). Con eso `search_router` pone `streamable` (`ver_de()`) y `reproduccion._armar()` arma el vídeo (`tramos_de()`, que lo mira en el momento si aún no se miró); **los clientes no han cambiado**. Dos formas de trocear: los **volúmenes de rar** (`.part1.rar`… o el esquema viejo `.rar`, `.r00`, `.r01`…, donde el `.rar` va **primero**) llevan cada uno su cabecera delante, y el vídeo es el trozo de datos de cada uno (por eso `Tramo` tiene `base`, dónde empieza dentro del mensaje); los **trozos** (`.zip.001`, `.7z.001`, `.rar.001`, o uno entero) son un archivo partido a bytes y el vídeo es un tramo continuo de la unión. El **7z** no tiene cabecera por archivo (la lista va al final, comprimida casi siempre): los datos empiezan en el byte 32, y almacenado ahí está el vídeo tal cual (o tras un `.nfo`), lo que se reconoce por su firma; dónde acaba lo dice el propio vídeo (el tamaño del Segment en MKV, las cajas en MP4, los bloques RIFF en AVI). Solo se ofrece si el vídeo es **casi todo el comprimido** (`MINIMO_VIDEO`, 90 %): un pack de temporada guarda diez episodios y «Ver» pondría el primero (clase `varios`). Con contraseña, `cifrado`. Al cambiar cómo se mira hay que subir `interior.VERSION`: lo guardado con otra versión se vuelve a mirar. Cuánto ha pasado de «Descargar» a «Ver»: `GET /api/admin/telegram/interior`. Probado en `backend/tests/prueba_interior.py`, que fabrica rar 4 y 5, zip y 7z (y con `ARCHIVOS_REALES=<carpeta>` compara además con los del `rar` oficial).
- **HLS al vuelo (`services/hls.py`, `/api/hls/index.m3u8`)**: lo que el aparato no abre tal cual —un MKV o audio AC-3/DTS en el iPhone, AC-3/DTS en Chrome de Android— lo reempaqueta ffmpeg mientras se ve: la imagen **se copia** (H.264 o HEVC, sin gastar CPU; otro códec no se ofrece) y el audio pasa a AAC estéreo, servido como HLS fMP4, que es el streaming nativo de Apple. Lo decide el reproductor del móvil (`modoDeReproduccion()`), preguntando al navegador si sabe HLS (`canPlayType`) y mirando las pistas (`/media/tracks` trae `hls`, que pone `comprobar` tras leer el índice del MKV). Lo difícil es **saltar**: copiando la imagen un trozo solo puede empezar en un fotograma clave, así que la lista tiene **un trozo por fotograma clave**, sacados del índice (Cues) del MKV sin bajar el vídeo (`mkv.fotogramas_clave`), y ffmpeg corta en cada uno (`-hls_time 0.1`), de modo que el trozo N de la lista es el N que fabrica. Tres cosas medidas, sin las que los saltos caen mal: `-ss` copiando la imagen **arranca un fotograma clave antes** del pedido (se mira el `tfdt` del primer trozo fabricado y se numera desde ahí, `desfase`); sin **`-noaccurate_seek`** el audio empieza en el punto exacto y la imagen en el fotograma clave anterior (segundos de desfase); y el muxer fMP4 lleva cada pista a 0 ignorando `-copyts`, salvo con **`movflags=+frag_discont`** (`-hls_segment_options`), que escribe el tiempo real. Una sesión (un ffmpeg) por archivo, que se reinicia si se pide un trozo lejos de lo fabricado, se pausa con SIGSTOP si va más de 40 trozos por delante de lo que se ve (para no bajarse la película entera) y borra lo que queda 30 trozos atrás; se cierran a los 5 minutos sin uso. **Solo las que recodifican tienen tope** (`RECODIFICANDO_MAX`, 6): las que copian la imagen casi no gastan y lo que las limita es el ancho de banda de Telegram. Con las 6 cogidas, la que lleve `SIN_USO_S` (90 s) sin pedir nada —cerrada o en pausa: un reproductor en marcha pide un trozo cada 4 s— deja su plaza; si todas están en uso, **el que llega recibe un 503** con `Retry-After` en vez de cortarle la película a otro, que es lo que pasaba antes (se cerraba la menos usada aunque alguien la estuviera viendo). Cambiar de idioma en un AVI reaprovecha la plaza de la sesión del mismo archivo. Solo **una pista de audio** (la preferida, `mejor_audio`) y **sin subtítulos**. **No es solo cosa del iPhone**: Chrome (Windows, Mac, Android) tampoco decodifica AC-3/E-AC3/DTS, así que un MKV como los de Better Call Saul (castellano e inglés en AC-3 5.1) **se veía y no se oía** en la web de escritorio, que mandaba el archivo tal cual. Ahora la web y el móvil deciden igual (`modoDeReproduccion()` + `useFuente()`, gemelos en `frontend/` y `mobile/`): si la pista que va a sonar —la primera o la de por defecto, no «alguna»— es de esas, se pide la versión adaptada, con el HLS del propio navegador en Safari/iPhone (es el que viaja por AirPlay) y con **hls.js** en el resto (Chrome 155 ya dice `maybe` a HLS, pero se prefiere hls.js). Para comprobar un caso en Chrome: `video.webkitAudioDecodedByteCount` se queda en 0 cuando el audio no se decodifica. **Los MP4 también se adaptan**: no traen una lista de fotogramas clave como el índice del MKV, así que `services/mp4.py` la saca de las tablas de la cabecera (`moov`) cruzando `stss` (cuáles son clave), `stts` (tiempo de decodificación), `ctts` (el retraso de los fotogramas B) y la lista de edición (`elst`, que corre la pista); el resultado es el tiempo que ve ffmpeg, y se comprobó idéntico a ffprobe en MP4 reales de Telegram (menos de 2 MB leídos, un segundo). La cabecera puede ir al principio o al final; un MP4 **fragmentado** no tiene esas tablas y no se adapta. Qué lector usar lo dicen los primeros bytes (`EBML`), no el nombre. Ojo: hay MP4 con un fotograma clave cada medio segundo, o sea listas de 8.000 trozos y varios MB con la entrada repetida en cada línea; por eso `/api/hls/index.m3u8` va **comprimida** (2 MB → 13 KB). **Los AVI se recodifican**: de 30 al azar del catálogo (~15.000 en total), 28 eran XviD/DivX —ningún navegador ni el iPhone lo decodifican, así que con «Ver» no salía ni la imagen— y 29 de definición estándar. Ahí no se puede copiar la imagen, así que `hls.modo()` devuelve `recodificar` para todo lo que no sea MKV/MP4 con H.264/HEVC **hasta 720p** (`ALTO_MAX`) y ffmpeg la pasa a H.264 (`veryfast`, 2 hilos). Es más sencillo que copiar: los fotogramas clave los pone ffmpeg (`-force_key_frames` cada `TROZO_S` = 4 s), así que el trozo N empieza en el segundo 4·N y **no hace falta leer ningún índice**, solo la duración; se arranca con `-ss` preciso (sin `-noaccurate_seek`) y `-output_ts_offset` en vez de `-copyts`. Lo que sí hace falta es que el AVI **traiga índice** (`avi_con_indice()`: la bandera AVIF_HASINDEX o un `indx` de OpenDML), o para saltar ffmpeg leería el archivo desde el principio; los 30 de la muestra lo traían. Medido en el servidor (i5-6500T): un XviD SD se recodifica a 9× tiempo real con un núcleo, el primer trozo sale en ~2 s y un salto tarda ~2,5 s. Un 1080p costaría unas cuatro veces más y se queda en «Descargar»: la web y el móvil lo dicen antes de abrir el reproductor (`motivoNoSeVe()`). La gráfica del servidor tiene Quick Sync, pero el contenedor no la ve y con SD no hace falta. Ojo con lo adelantado que va ffmpeg: se mide con lo que ha hecho **su tanda** (`hecho`), no con todo `listos`, donde siguen los trozos de tandas anteriores; con eso una tanda vieja que llegó lejos dejaba a la nueva pausada (SIGSTOP) nada más arrancar y volver al principio tras un salto no cargaba nunca. Y se vigila cada 2 s en el limpiador, no solo al pedir un trozo: con el buffer del reproductor lleno no se pide nada y ffmpeg se bajaba la película entera. **El índice de un MKV no siempre apunta a todos los fotogramas clave**, y ffmpeg corta en todos: con «2x03 Tulsa King [HDTV 1080p].mkv» (uno cada 2 s en el vídeo, uno cada 6 s en las Cues) cada trozo de la lista eran tres piezas de ffmpeg, y numerándolas por orden el último trozo (2554 s) llevaba dentro el segundo 2259; hls.js lo cargaba, bajaba la duración a lo que tenía y **daba el capítulo por terminado a los 35 minutos de 42** (de ahí la pantalla del final a mitad y, al volver, el vídeo desde cero). Ahora cada pieza se coloca por su `tfdt` y no por su número, un trozo se sirve con todas las suyas juntas (`hls.juntar()`, fragmentos fMP4 seguidos) y solo cuenta como hecho cuando ya hay una pieza del siguiente (o ffmpeg ha acabado). Y **solo la petición más reciente mueve ffmpeg** (`s.pedido`): tras un salto, la petición del trozo de antes sigue viva en el servidor aunque el reproductor ya no la quiera, y cuando las dos podían reiniciarlo cada una lo llevaba a lo suyo matando lo de la otra (ffmpeg arrancando en el 4 y en el 412 decenas de veces en un segundo, hasta que las dos se rendían y el vídeo se quedaba vacío); ahora la vieja se retira. Probado con un ffmpeg de verdad en `backend/tests/prueba_hls.py` (también con un índice que apunta a uno de cada dos y con un salto con una petición vieja esperando).
- **Los clics no salen del reproductor de la web**. `Player` se monta dentro de la ficha (`TitleSheet`), cuyo fondo lleva `onClick={onClose}`, y en React los eventos suben por el **árbol de componentes**, no por el de la página: aunque el reproductor tape la pantalla entera, un clic en la barra de progreso llegaba al fondo de la ficha y la cerraba, llevándose la película. Se vio al «elegir un minuto» viendo sin descargar, pero pasaba igual con lo descargado. El `div` raíz del reproductor corta la propagación; los avisos de la ficha (`pick`, `noSeVe`) también.
- **Las partes de un archivo se buscan en el catálogo, no en Telegram**. `find_related_parts()` hacía una búsqueda en Telegram por canal, en serie y sin límite de tiempo; Telegram raciona las búsquedas y Telethon, ante un `FloodWait` corto, **se duerme en silencio** hasta un minuto por llamada, así que «Descargar» se quedaba sin contestar y parecía que no hacía nada. Ahora las busca en `media_items` del mismo canal y solo pregunta a Telegram si el catálogo no las tiene (8 s por canal), y `iniciar_descarga` corta a los 30 s con un error en vez de colgar. Si tarda más de 5 s queda un `WARNING` en el log.
- **Mensajes nuevos**: se indexan en tiempo real con un handler `events.NewMessage` de Telethon (`watch_new_messages()` → `index_live_message()`); el filtro de canal se evalúa en cada evento, así que los canales añadidos después también cuentan. `run_full_index` ya **no omite** los canales `done`: los escanea desde `last_message_id` (solo lo nuevo), al arrancar y en el barrido periódico (`periodic_rescan`, `TMD_RESCAN_HOURS`).
- **Mensajes nuevos: el filtro va por `channel_ids`, no por `channels`**. `watch_new_messages()` comparaba el `chat_id` del evento contra `self.channels`, que solo tiene los canales que Telethon ha conseguido **resolver**; si `get_entity` fallaba para uno (pasa con canales privados o a los que la cuenta no llega), sus mensajes nuevos se descartaban en silencio y lo que se publicara ahí no se indexaba nunca. Ahora se compara contra la lista de canales activos, y `channel_name()` da el nombre aunque el canal no esté resuelto. Todo lo que llega queda en la tabla `novedades` con el motivo del descarte, y se ve en la pestaña **Novedades** del panel: un mensaje ignorado ya no desaparece sin dejar rastro.
- **El bucle de TMDB no sale de golpe**: `ensure_enrich_worker()` no arranca otro mientras haya uno vivo, así que un mensaje que llegara justo cuando el bucle iba a terminar se quedaba sin enriquecer — y como en la Home solo sale lo `tmdb_valid`, esa película no aparecía hasta el siguiente barrido (horas). `_enrich_loop()` espera ahora un margen (4 comprobaciones de 5 s) antes de cerrar.
- **Tareas de fondo**: usa `spawn()` de `app/tasks.py`, no `asyncio.create_task()` a secas. Este último se traga las excepciones y mantiene solo una referencia débil a la tarea; así estuvo roto el indexado al añadir un canal sin que apareciera nada en los logs.
- **App de TV (`tizen/`, `webos/` para LG, `firetv/` para los Fire TV Stick y `/ps4/` para el navegador de la PlayStation)**: un solo código en `tizen/src`; `webos/` y `firetv/` solo empaquetan (`appinfo.json`, `build.sh` genera el `.ipk` con `vite --mode webos`, objetivo Chromium 53 —ver webOS 4 más abajo—, y `deploy.sh` instala con el CLI `ares-*` que va como devDependency de `tizen/`). Diferencias por plataforma ya resueltas en código: salida (`tizen.application.exit` / `window.close`), cursor (solo Tizen lo oculta; el Magic Remote de LG enfoca al pasar), nada de `gap` en flex (webOS 5/6 no lo soporta: `space-x`/`space-y`). Interfaz propia, no un calco de la web. Mide 1920×1080 fijos (px absolutos, sin breakpoints; `main.tsx` la escala en desarrollo). Estructura: `components/Rail` (navegación lateral, vive fuera de las rutas), `Screen` (columna de contenido con scroll por transform + `Hero`, el panel que describe la tarjeta enfocada vía `tv/featured.ts`), `Row`/`PosterCard` (carriles), `TitleDetail` (ficha a pantalla completa), `Player` (reproductor sin controles nativos; teclas en `focus/keys.ts` `pushRawHandler`/`pushMediaHandler`), `Keyboard` (teclado en pantalla). Los paneles a pantalla completa se montan por portal en `#overlays` (`components/Overlay`): dentro de la columna con transform, `position: fixed` no funciona. Un solo `DownloadsProvider` para descargas + índice de disco. Reglas de render: solo se animan transform/opacity, nada de backdrop-filter, el foco es una clase CSS. Los tests del motor de foco: `npm test`.
- **LG con webOS 4 (2018-2019): `/tv-webos/` y no `/tv/`**. Llevan Chromium 53, que **no carga `<script type="module">`**: lo ignora sin un error y la app se queda en negro (pasó con una 32LM6380PLC, webOS 4.5). En los modos `webos` (el `.ipk`) y `tv-webos` (lo que ese paquete se baja del servidor) `@vitejs/plugin-legacy` compila además un paquete clásico (`nomodule`, SystemJS, polyfills de core-js), y el CSS pasa por `tizen/postcss.webos4.js`, porque Chromium 53 descarta la declaración entera ante `rgb(20 20 20 / x)` y `#0000` (fondos, bordes y el anillo del foco), la regla entera ante `:where()` (los botones salían grises) y no tiene CSS Grid (el teclado salía en una columna; se rehace con flex dentro de `@supports not (display: grid)`). Va en una compilación aparte para que `/tv/`, Samsung, Fire TV y PS4 no cambien **ni un byte** (comprobado comparando los builds); por eso en `main.tsx` la ruta va escrita en línea y no en una constante, que haría al minificador renombrar variables. En webOS 4 el inspector se desconecta con `Page.captureScreenshot`: se comprueba evaluando JavaScript (`ares-inspect` + CDP en el puerto 9998).
- **Fire TV (`firetv/`)**: Fire OS es Android, así que la app es un APK: una `Activity` con un `WebView` a pantalla completa que carga el mismo build de `tizen/src` (modo `firetv`, objetivo Chromium 68 como webOS). `build.sh` **no usa Gradle**: sin dependencias sale más rápido llamando a `aapt2`, `javac`, `d8` y `apksigner` a mano. El SDK vive en `/Volumes/Sandisk/android-sdk` (disco externo) y la firma en `~/.moviesandchill-firetv.keystore` — si esa clave cambia, el Fire TV obliga a desinstalar antes de actualizar. Tres cosas que hay que saber: el botón **Atrás** del mando no llega al WebView como `keydown`, se lo queda la Activity y se reenvía con `window.__tvBack()`; **salir** no lo puede hacer la web sola (`window.close()` no cierra una Activity), va por el puente `AndroidTV.exit()`; y sin **`LEANBACK_LAUNCHER`** más `touchscreen required="false"` en el manifest la app se instala pero no sale en la fila del Fire TV. `tizen/.env.firetv` apunta a la IP local y no al dominio público porque una película son varios GB; por eso el manifest lleva `usesCleartextTraffic`.
- **Las apps de televisión se actualizan solas porque la interfaz la sirve el servidor**. Un `.wgt`, un `.ipk` y un `.apk` se instalan a mano, así que cada arreglo de la interfaz obligaba a levantarse del sofá. Ahora el paquete instalado es **solo el arranque**: comprueba si el servidor sirve `/tv/` y le pasa el control, de modo que al abrir la tele ya está la última versión (es lo que se hizo con la PS4 por obligación, aquí por comodidad). La dirección sale de `VITE_API_BASE`, que ya va dentro de cada paquete; el build servido se compila **sin ella** (`tizen/.env.tv`), así que Vite elimina el reenvío del bundle y la versión servida no puede reenviarse a sí misma. Cinco detalles que lo sostienen: si el servidor no contesta **en un segundo y medio** se sigue con la copia del paquete (una interfaz vieja que funciona es mejor que una pantalla en negro); no basta con un 200, se busca la marca `<div id="app"` porque un portal cautivo también contesta 200; no se monta React antes de decidir, o se vería un arranque doble; en Tizen hace falta `<tizen:allow-navigation>` además de `<access>`, porque `access` solo abre las peticiones XHR y no el *navegar* fuera del paquete; y en el Fire TV la comprobación va en el lado nativo (`MainActivity.cargarInterfaz()`) para no arrancar la copia del APK y tirarla después, lo que obliga a hacerla **en otro hilo**, porque Android no deja tocar la red en el de la interfaz. Dos consecuencias: la primera instalación sigue siendo a mano, y al pasar de la copia instalada a la servida **cambia el origen**, así que hay que entrar una vez más (la sesión se guarda por origen). De regalo, cargada del servidor la interfaz y la API comparten origen y las llamadas dejan de ser cross-origin.
- **Fire TV: la interfaz no se carga con `file://`**. Vite empaqueta el bundle como **módulo ES** (`<script type="module">`) y un módulo se descarga con las reglas de CORS; un documento `file://` tiene origen opaco, así que el WebView bloquea su propio script y **la pantalla se queda negra sin un solo error en pantalla** — el HTML carga y el JS no llega a ejecutarse. En Tizen y webOS no pasa porque sus runtimes se abren los permisos de `file://` por su cuenta; el WebView de Android no. `MainActivity` sirve los assets del APK bajo `http://appassets.androidplatform.net` interceptando en `shouldInterceptRequest` (lo mismo que `WebViewAssetLoader` de androidx, a mano para no meter Gradle). Dos detalles que lo rompen: un `.js` servido con un MIME que no sea de JavaScript **no se ejecuta** como módulo, y el origen pasa a ser `http`, así que las llamadas a la API son **cross-origin** y dependen de `TMD_CORS_ORIGINS` (con `*` van; ojo si algún día se cierra).
- **Fire TV: `innerWidth` miente, hay que mirar `visualViewport`**. El Stick tiene 1920×1080 físicos pero densidad 320 dpi, o sea **960×540 px CSS**. Como el lienzo de la app mide 1920 fijos, el WebView **ensancha el viewport de maquetado** hasta que quepa: `innerWidth` pasa a valer 1920 (el ancho del lienzo, no el de la tele), el `fitToWindow()` de `main.tsx` calculaba `k = 1`, no escalaba nada y **la app se dibujaba al doble, viéndose solo el cuarto de arriba a la izquierda**. Se toma el menor de `innerWidth` y `visualViewport.width`: donde no hay nada raro valen lo mismo, y donde el maquetado se ha estirado manda el visual. Es estable (al escalar a 0.5 deja de desbordar y los dos se igualan en 960). La PS4 no tiene `visualViewport`, de ahí el respaldo.
- **Fire TV: los recursos necesitan calificador de densidad**. Un PNG en `res/drawable/` o `res/mipmap/` **a secas se interpreta como mdpi**, así que en una pantalla de 320 dpi Android lo escala ×2: el banner de 1280×720 acababa midiendo 2560×1440 y el lanzador solo enseñaba una esquina del logo. Van en `drawable-<densidad>/` y `mipmap-<densidad>/` con las medidas canónicas (banner 320×180 en xhdpi, icono 96×96). Los originales están en `firetv/art/` para poder regenerarlos.
- **Fire TV: una captura con `adb screencap` sale siempre negra**. El WebView de Amazon compone sobre un *SurfaceView* y `screencap` no captura esas superficies, solo el fondo de la ventana (un PNG liso de `#141414`). **No es síntoma de pantalla en blanco.** Para ver de verdad lo que hay, `MainActivity` deja activado `setWebContentsDebuggingEnabled(true)`: `adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>` y por el protocolo de Chrome se lee el DOM, se evalúa JavaScript y se saca la captura con `Page.captureScreenshot`. Los `console.log` de la interfaz van además a logcat con la etiqueta `MoviesChill`.
- **PlayStation 4 (`ps4/`)**: no hay app nativa posible —Sony solo admite socios con *dev kit* aprobado, no hay *sideload*— así que la app se **sirve por web**: `frontend/Dockerfile` compila `tizen/src` en modo `ps4` y nginx la publica en `/ps4/`, con el redirector de `frontend/index.html` mandando la consola ahí igual que manda los teléfonos a `/m/`. Tres cosas que la distinguen de una tele. **El objetivo de compilación no es Chromium**: la PS4 lleva WebKit, y con `chrome68` (el de webOS) el paquete sale con sintaxis que la consola no lee y la página se queda en blanco; el modo `ps4` compila para `safari11` y `tv/polyfills.ts` añade `flat`/`flatMap`, que esbuild transpila pero no inventa (sin ellos la pantalla de Descargas se queda vacía con un TypeError en una consola donde nadie va a mirar). **No llega ninguna tecla**: el navegador no expone la Gamepad API, el mando es un cursor y ✕ un clic, así que lo que en una tele se pulsa en el mando tiene que estar dibujado (`soloPuntero()` en `tv/platform.ts` enciende el botón Volver de la ficha y los de pausa, saltos e idioma del reproductor, y apaga «Salir de la app», que en una página no hace nada); el interfaz ya era clicable por el Magic Remote de LG, así que lo único que faltaba de verdad era el reproductor. Y **los códecs son más estrechos que en todo lo demás**: solo H.264 de 8 bits en 4:2:0 hasta 1080p con AAC, nada de HEVC ni 10 bits, de modo que parte de la biblioteca —que es correcta en el resto de aparatos porque `make_compatible()` deja pasar el HEVC— aquí **se oye pero no se ve**, sin ningún error. Es el mismo fallo que costó cuatro diagnósticos con AirPlay, así que se avisa antes: `video_apto_ps4()` en `services/tracks.py` lo decide, `/api/media/tracks` lo devuelve y el reproductor lo dice con el motivo y la opción de intentarlo igualmente. Con un teclado USB enchufado a la consola las flechas y Enter funcionan como en una tele.
- **«Continuar viendo» lo guarda el servidor, no el aparato**. Vivia en el `localStorage` de cada cliente, y por eso casi no servia: lo empezado en la tele no existia en el movil, y **en la web ni siquiera habia donde verlo** (se guardaba la posicion y no habia fila que la enseñara). Ahora va en `playback_progress`, con clave `(user_id, path)` y la ruta **relativa a la biblioteca** — la absoluta cambia entre Docker y el modo de desarrollo, y entonces el mismo video seria otro. El `localStorage` se queda solo como **cache**: pinta la fila al instante al abrir y aguanta un corte de red (`cachedContinueWatching()`), y lo que cada aparato tuviera guardado de antes se sube una sola vez con `POST /api/progress/import`.
- **Una tarjeta por titulo, y la decide la ficha antes que la carpeta**. Lo visto sin descargar (`tg:<canal>:<mensaje>`) no tiene carpeta ni «3x05» en la ruta, así que agrupando por carpeta cada capítulo salía como una tarjeta (pasó con «Cyberpunk: Edgerunners» y «The Office»). Ahora `clave_titulo()` agrupa por `tmdb_id`/tipo y solo sin ficha por carpeta, y el capítulo y la ficha de esas rutas salen del catálogo: al guardar (`ficha_de_tg`) y, para lo ya guardado, al leer (el `LEFT JOIN media_items` de `_HISTORIAL`, con un `CASE` porque dentro de un AND Postgres puede convertir antes de comprobar el formato). De cada serie sale **el capítulo más avanzado** (temporada y episodio más altos) entre los que valen —empezados de verdad y reproducibles, o terminados—, no el último que se tocó: volver a ver el 2x03 no tapa que vas por el 4x08, y un capítulo abierto diez segundos no hace desaparecer la serie. «Quitar» una tarjeta olvida todas las filas de ese título, descargadas o no. Lo de abajo sobre la carpeta sigue valiendo para lo descargado sin ficha.
- **Una tarjeta por titulo, y la decide la carpeta**. La columna `grupo` es la carpeta de primer nivel dentro de la biblioteca, asi que los episodios de una serie y **las dos calidades de una pelicula** comparten tarjeta y solo sale lo ultimo que se vio; si no, dejar tres episodios a medias de la misma serie llenaba la fila con esa serie. La estructura antigua (`Suits S1/`, `Suits S2/`) se agrupa quitando el sufijo de temporada, igual que hace `/files`: sin eso cada temporada seria un titulo distinto y el episodio siguiente nunca cruzaria de una carpeta a otra.
- **Lo terminado no se borra, se marca**. Al acabar un episodio los clientes llamaban a `clearWatched()`; ahora se guarda con `position = duration`, porque **una fila terminada es justo lo que permite ofrecer el siguiente**. Quien decide que sale de la fila es el servidor: si el siguiente no esta en disco, el titulo desaparece. Se salta lo que ya se vio entero, o a quien se viera el 8 y volviera al 7 se le ofrecia el 8 otra vez. La tarjeta del siguiente **recalcula su etiqueta** (`3x08`): la guardada es la del episodio anterior y poner «3x07» sobre el 3x08 confunde justo donde hay que fiarse de lo que pone.
- **Lo último buscado es de la cuenta, no del aparato**. Estaba en el almacenamiento del navegador, con dos problemas: se queda escrito en un aparato que puede ser de más gente, y no sirve de nada en el resto (buscas algo en el móvil y en la tele no está). Vive en `user_state`, que es el gemelo por usuario de `app_settings` y la respuesta a «¿dónde pongo este dato de interfaz?»; las claves son una lista cerrada a propósito. Dos cuidados en el cliente. Se guarda **con retardo** (1,5 s) porque el buscador dispara una búsqueda por tecla y si no serían veinte escrituras por título, y lo que se manda al cumplirse el retardo es **lo último que se sabe**, no el valor con el que se programó: entre una cosa y otra han pasado varias teclas. Y no se guarda nada **hasta haber leído** lo que había: al entrar el campo está vacío, y guardar ese vacío borraría el término antes de poder recuperarlo (`ultimaBusquedaEnMemoria() === null` es la guarda).
- **Lo único que vive en el navegador es la sesión**. El almacenamiento es del *aparato* y los datos son de la *cuenta*: en un móvil o una tele que use más de una persona, todo lo que se guarde ahí se acaba viendo desde otra cuenta. Ya pasó dos veces (la fila de «Continuar viendo» y el nombre de usuario que el formulario de entrada rellenaba solo), así que la regla es que en `localStorage` solo están `access_token`/`refresh_token` —y en `sessionStorage` si no se marcó «Recuérdame»—. Lo que haga falta recordar entre pantallas va en una **variable de módulo** (la caché de «Continuar viendo», los carriles de la portada): se va al recargar, y eso es exactamente lo que se quiere. Lo que tenga que sobrevivir va al servidor, que es quien sabe de quién es cada cosa. La única excepción es `mc.desktop` en `frontend/index.html` («en este teléfono quiero la web de escritorio»), que no es de nadie en concreto y tiene que leerse **antes** de que cargue la app, porque es lo que decide el redirector. Al cargar, los tres `progress.ts` borran además las claves que dejaron las versiones anteriores (`mc.continuar`, `mc.progress`, `mc.continuar.migrado`): era historial de la cuenta guardado en el aparato.
- **«Continuar viendo» salía con películas de otro usuario**. Dos causas, las dos por confundir *el aparato* con *la cuenta*. La gorda: `importLocalProgress()` subía a la cuenta que estuviera dentro el historial que ese **navegador** tenía guardado de la época en que el progreso vivía en `localStorage` — y ese historial es del aparato, no de nadie en concreto, así que en una tele o un móvil compartidos el primero que abriera la app se quedaba con lo que hubiera visto el otro. Encima estuvo fallando en silencio (el 404 de `/api/api/progress/import`) y se reintentaba en cada arranque, de modo que **se importó todo de golpe el día que se arregló la ruta**, que es cuando aparecieron los fantasmas. La importación se ha quitado entera (y el endpoint con ella): era una migración de una sola vez y el precio de equivocarse es meterle a alguien en la cara lo que ve su familia. La otra: la caché de la fila (`mc.continuar`) es del navegador y no se tocaba al cambiar de cuenta, así que al entrar con otro usuario se pintaba la fila del anterior hasta que contestara el servidor (o para siempre sin red); ahora se olvida al entrar y al salir. Y en el móvil **no había forma de quitar una tarjeta**, que es lo que hacía el fantasma inmortal: ya tiene su botón, como la web. Quitar la importación impide que entren más filas ajenas, pero **no borra las que entraron**, que siguen en `playback_progress` a nombre de quien abriera la app ese día; para eso está «Vaciar mi Continuar viendo» (`DELETE /api/progress?todo=true`) en el perfil del móvil y en Mi cuenta. Si alguien vuelve a preguntar por qué le sale algo que no ha visto: la fila se monta con `WHERE p.user_id = $1` y cada tarjeta sale de una fila **suya**, así que el servidor no puede mezclar cuentas; lo que aparece es herencia de aquello, y una fila importada que estaba terminada se ve además como «una serie que ha empezado otro», porque el servidor ofrece el episodio siguiente.
- **La carátula de «Continuar viendo» la pone el servidor**. La tarjeta salía con un hueco gris y el título escrito, porque lo que se guarda en `playback_progress` es lo que manda el cliente y no todos saben la carátula: reproducir desde Descargas, desde una búsqueda o un archivo suelto guardaba la posición sin imagen. Teniendo `tmdb_id` la imagen está a un JOIN de distancia, así que `list_progress` la completa con `COALESCE(lo guardado, lo de tmdb_cache)`; y **sin `tmdb_id` queda el nombre**: la carpeta del título la puso `layout.py` con el título de TMDB, así que «Dune (2021)» encuentra su ficha quitándole el año (en `LEFT JOIN LATERAL` con `LIMIT 1`, porque el título no es único y un join normal duplicaría la tarjeta) —en ese orden, porque lo del cliente puede ser el fotograma de un episodio concreto— y además las pantallas de Descargas ya pasan la ficha al reproductor. Para lo que no tiene imagen en ningún sitio (un título que TMDB no conoce) las tarjetas pintan una **carátula generada**: un degradado estable sacado del nombre (`fondoDeTitulo()` en `utils/text.ts`), que es lo que ya hacía la app de la tele. Un hueco gris parece que la tarjeta se ha roto; un degradado con el título, no.
- **El ultimo guardado necesita `keepalive`**. Cerrar la pestaña, bloquear el telefono o salir de la app **no desmonta el reproductor**, asi que el `useEffect` de limpieza no corre y se perdia justo el minuto por el que se dejo la pelicula, que es el unico que importa. Los tres reproductores escuchan `pagehide` y `visibilitychange`, y esa peticion va con `keepalive: true`: sin el, el navegador la cancela en cuanto se va la pagina.
- **El reproductor de la tele reanudaba en bucle**. Al poner un capítulo, el vídeo saltaba al minuto guardado una y otra vez, sin parar. La causa: el efecto grande del `Player` dependía de `onClose`, y en la ficha eso era `() => setPlaying(null)` —**una función nueva en cada render del padre**—, así que cada render desmontaba el efecto, lo volvía a montar, volvía a pedir el punto de reanudación y lo volvía a aplicar; y como `save()` va guardando la posición cada cinco segundos, el punto al que saltaba también avanzaba. No se vio hasta que se arregló `/api/api/progress`: antes el progreso no llegaba al servidor, el punto era siempre 0 y aplicarlo no movía nada. Dos capas de arreglo, porque una sola dejaba el fallo a un render de distancia: el guardia de «ya reanudado» vive en un `useRef` (sobrevive a que el efecto se vuelva a montar, y se guarda **por ruta** para que volver a abrir el mismo archivo sí reanude), y el efecto depende solo de `path` con las funciones por referencia, de modo que ya no se desmonta diez oyentes y los vuelve a montar en cada render. Los `onClose` de `TitleDetail` y `Library` van además en `useCallback`: ahí estaba el origen.
- **El punto de reanudacion llega tarde**. Lo da el servidor, asi que puede resolverse antes o despues de que el `<video>` tenga metadatos. Lo aplica el que llegue el ultimo de los dos (`loadedmetadata` o el `.then`), una sola vez. Donde hace falta sincrono —la ficha, para decir «Continuar viendo» en vez de «Reproducir»— se usa `cachedResumePoint()`, que lee la cache; con la cache fria dira «Reproducir» pero el reproductor reanuda igual.
- **Favoritos**: viven en `user_favorites (user_id, tmdb_id, media_type)` y la clave lleva el **tipo de TMDB** (`movie`/`tv`), no el del cliente (`movie`/`series`): sin él, `tv/606` y `movie/606` serían el mismo favorito. `favorites_router._tipo_tmdb()` traduce en la frontera. La fila **«Mis favoritos» la monta el servidor** dentro de `/browse/home`, así que sale igual en la web, el móvil y la tele sin que ninguno la arme por su cuenta; cada app añade encima su pantalla (`/favoritos`) y el corazón en la ficha. Al leer la lista, los archivos entran por `LEFT JOIN`: si se da de baja el canal que traía la película, el favorito sigue ahí con 0 archivos en vez de desaparecer sin que nadie lo haya quitado. El corazón se pinta al tocarlo y se deshace si el servidor dice que no.
- **La pantalla de Favoritos va clasificada**: primero por tipo (Películas · Series) y dentro de cada uno por género. Lo agrupa `utils/favorites.ts` (`groupFavorites()`, el mismo archivo copiado en web, móvil y tizen) sobre los `genres` que `/favorites` ya devuelve, así que **no hace falta nada del servidor**. Un título cae en **un solo** grupo, el de su **primer** género en TMDB: TMDB da dos o tres por título y repetirlo en todos dejaría «12 títulos guardados» arriba y veinte carátulas debajo. Los géneros van del más lleno al más vacío (a igualdad, alfabéticos) y «Sin género» siempre al final. Cada app lo pinta como le toca: la web apila las dos secciones (pantalla ancha, se abarca de una pasada), el móvil las pone en un conmutador (con tres carátulas por fila, apiladas dejarían las series a varias pantallas) y la tele hace un carril por pareja («Películas · Acción»), porque con el mando no hay dónde enfocar un encabezado.
- **Contadores de Canales: se sigue preguntando aunque el escaneo haya acabado**. `Channels.tsx` hacía `setPolling(false)` en cuanto ningún canal estaba `running`, y ahí se paraba el `setInterval`: los mensajes que llegan en vivo (`watch_new_messages`) sí se indexaban, pero el panel se quedaba congelado en el número que hubiera al terminar hasta recargar la página. Ahora el estado solo decide **cada cuánto** se pregunta (5 s escaneando, 20 s en reposo, y nada con la pestaña oculta). `get_index_stats()` es un `COUNT(*)` en vivo, así que el dato nunca estuvo rancio: lo que faltaba era volver a pedirlo.
- **Las cuatro cifras del móvil van en rejilla de dos**. En una sola fila le tocaban ~70 px a cada una y `160.684` no cabía: los números salían enormes y pegados al borde, y «Con ficha» se recortaba. En `grid-cols-2` cabe el número entero con aire.
- **Varias calidades de la misma pelicula**: 4K y 1080p son **dos descargas distintas y conviven**. Antes las dos caian en `<Titulo (Año)>/<Titulo (Año)>.mkv` y `finalize_episode()` hacia `os.remove(dst)` si el destino existia: la segunda **borraba a la primera sin avisar**. Ahora el nombre lleva la calidad (`etiqueta_calidad()` en `layout.py`: `Titulo (Año) - 2160p BluRay.mkv`) y `ruta_libre()` nunca pisa nada —si coincide, ` (2)`—. Tres cosas iban enlazadas con esto: `find_existing()` comparaba **tambien la carpeta** de destino, asi que teniendo el 1080p el 4K se rechazaba con «Ya está descargado»; una pelicula **poseia su carpeta** (`downloads.folder_path`), de modo que las dos versiones compartian fila y borrar una borraba las dos (y el dueño que salia era el de cualquiera); y `/files` decidia «es serie» por **cuántos** videos hay en la carpeta, asi que dos calidades salian como una serie de dos episodios. Ahora se posee el **archivo** (igual que un episodio), lo que decide si es serie es que el nombre lleve **marcador de episodio** (`1x01`, `S01E01`), y `/files` devuelve `versions[]` por pelicula con su calidad, tamaño y dueño. Los tres clientes piden cuál ver y borran solo esa.
- **Una descarga interrumpida al apagar se quedaba colgada para siempre**. La fila nace apuntando a la carpeta de trabajo (`.dl_<lote>`) con estado `downloading`, y de ahi solo la sacan `move_download()` al terminar o `delete_download()` al cancelar — las dos viven en el proceso. Si el backend se para en mitad de una descarga (**un redespliegue basta**), nadie vuelve a tocar esa fila. Y no es cosmetico: `downloading` esta en `ACTIVE_STATES`, asi que la descarga fantasma **le sigue comiendo cuota a su dueño**, `find_existing()` la da por viva y **nadie puede volver a bajar ese titulo**, y borrarla desde la app tampoco se puede («esta descarga sigue en curso: cancelala antes»). Sin salida por ningun lado: le paso a `elpajas` con un episodio de Final Space, 1,08 GB de cuota por una carpeta temporal que ya ni existia en disco. `reconciliar_interrumpidas()` corre al arrancar —donde nada puede estar descargando todavia— y resuelve cada fila de menos a mas destructivo: si el lote sigue en `paused_batches.json` la pone en `paused` y **no toca el disco** (las partes ya bajadas se reanudan), si la ruta ya no es la carpeta de trabajo y existe la da por `done` con su tamaño real, y si no borra lo que quede, poda las carpetas vacias y olvida la fila. Probado en `backend/tests/prueba_descargas_colgadas.py`.
- **`downloads` ya no tiene indice unico en `folder_path`** (varios episodios comparten carpeta de temporada, asi que la ruta se repite). Eso deja fuera cualquier `ON CONFLICT (folder_path)`: PostgreSQL rechaza un `ON CONFLICT` cuya columna no tenga restriccion que lo respalde, con «there is no unique or exclusion constraint matching». `adopt_orphans()` lo llevaba y no saltaba nunca porque el bucle ya descarta lo que tiene dueño; usa ahora `INSERT ... SELECT ... WHERE NOT EXISTS`, que no depende de ningun indice. Al añadir un `ON CONFLICT` nuevo, comprobar que la columna sigue teniendo su restriccion.
- **Lo que posee una descarga no siempre es un archivo**. Lo es en lo que se baja ahora (cada calidad y cada episodio poseen el suyo), pero no en lo anterior ni en nada de lo que adopta `adopt_orphans()`, que registra lo que encuentra en la raíz de la biblioteca —y para una película eso es su **carpeta**—. Esa ruta salía tal cual en `local_path`, acababa en el `src` del `<video>` y `/api/stream` contestaba **404** porque no es un archivo: el reproductor del móvil decía «no se ha podido abrir el vídeo, puede que el archivo no esté listo todavía» al darle a una película **que había bajado otro**, que es otra forma de decir «que se bajó antes». Lo resuelve `video_en()` (`services/layout.py`) al construir `local_path`, así que vale para los cuatro clientes. Ordena por **nombre y no por tamaño** a propósito: en una carpeta de temporada eso da el `1x01`, que es por donde se quiere empezar, y en una de película con dos calidades da la película igual; por tamaño acertaría la calidad y fallaría el episodio. Probado en `backend/tests/prueba_video_en.py`.
- **Cuentas, cuotas y dueños**: `users.quota_bytes` (NULL = sin límite) y `users.active`. Cada descarga tiene dueño (`downloads.owner_id`); la cuota compara el disco que ocupan sus descargas vivas (`downloading|paused|done`) con `quota_bytes` antes de aceptar otra. **Una descarga la ve todo el mundo, solo la borra su dueño o un admin, y nadie puede volver a bajar lo mismo** (`POST /download` devuelve `already: true` con el dueño). `/files` devuelve `owner` y `can_delete`; `DELETE /files` los comprueba. Lo anterior a esta versión pasó al admin al arrancar.
- **Varias pistas de audio activas = todos los idiomas a la vez**. La conversion hacia `-map 0:a` y el ffmpeg del servidor (7.1.5) deja **todas** las pistas marcadas como activas en el `tkhd`; Safari y QuickTime reproducen todas las activas a la vez. Se comprobo sobre `Oppenheimer (2023).mp4`: tres pistas (spa, spa, eng) con `default: true` las tres. `_mapeo_audio()` en `compat.py` pone delante el español, lo deja como unica activa con `-disposition:a:N` y etiqueta el idioma de todas. Ojo: ffmpeg 9 ya lo hace solo, asi que el fallo **no se reproduce** con un ffmpeg moderno en local — hay que mirar las banderas del `tkhd`, no lo que diga `ffprobe -show_entries disposition`. Un MP4 que ya era compatible se arregla con un remux copiando, y la revision de biblioteca (`convert_library_job`) ya no salta los `.mp4` por serlo.
- **`mediainfo --Inform=Audio;%Format%` pega el formato de todas las pistas**: con tres audios devuelve `AACAC-3EAC3`, así que `"aac" in anorm` daba **compatible** en cuanto una sola lo fuera. Un archivo con el español en AC-3 y el inglés en AAC pasaba de largo, se copiaba el audio tal cual (`-c:a copy`) y `_mapeo_audio()` dejaba el AC-3 como pista activa: ni el iPhone ni Chrome decodifican AC-3/E-AC3/DTS, así que **la película se ve y no se oye**, sin ningún error (un Apple TV o una tele sí lo sacan, de ahí que parezca cosa del teléfono). Lo decide ahora `audio_apto_apple()` en `services/tracks.py`, pista por pista y con ffprobe, igual que `video_apto_apple()` con los 10 bits; `GET /api/media/tracks` lo devuelve (`audio_apple`, `audio_apple_motivo`). Para arreglar lo ya descargado hay que volver a pasar la revisión de biblioteca (`POST /api/admin/convert-library`), que ahora sí reencodea esos audios a AAC.
- **Subtitulos a `.vtt` sueltos** (`services/subs.py`), con el nombre `<video>.<idioma>[.forced].vtt` al lado del video. MP4 no admite PGS ni ASS y antes se tiraban con `-sn`; una pista de subtitulos dentro del MP4 tampoco sirve porque Chrome la ignora. Los de imagen (PGS, VobSub) se siguen descartando: son fotogramas. Se sirven por `GET /api/subtitle` y se borran con su video.
- **Cambiar de pista de audio lo hace el servidor**. `video.audioTracks` solo existe en Safari (y en algunas teles): Chrome, el WebView del Fire TV y Chrome de Android no lo implementan y suena siempre la primera pista; además la versión adaptada (HLS) solo lleva una. Así que al elegir otro idioma, si no hay `audioTracks` o se está viendo por HLS, el reproductor pide `/api/hls/index.m3u8?...&audio=N` (N = `order` de la pista, la posición 0:a:N) y vuelve al mismo segundo al llegar `loadedmetadata`; mientras recarga no guarda la posición (el `<video>` nuevo empieza en 0). Cada pareja archivo-idioma es su propia sesión de ffmpeg (`clave_sesion`), y **el HLS acepta ya archivos de la biblioteca**, no solo rutas `tg:` (`_Local` en `hls.py`), que es lo que permite cambiar de idioma en lo descargado. En Safari con un archivo tal cual se sigue usando `audioTracks`, que es instantáneo. La conversión sigue poniendo el español el primero, que es lo que suena sin tocar nada. Probado en `prueba_hls.py` (dos pistas, una floja y otra fuerte). En el movil no hay selector propio: el reproductor es el nativo del sistema y ya trae el suyo, solo se le cuelgan los `<track>`.
- **MP4 obligatorio**: iPhone/Safari no reproduce MKV, así que `make_compatible()` deja todo en MP4 (contenedor MKV ya no cuenta como compatible; HEVC se etiqueta `hvc1`; sin subtítulos porque MP4 no admite PGS/ASS). El interruptor sigue llamándose `convert_dts_to_ac3` por compatibilidad con el `.env`.
- **Sesión de Telegram sin consola**: `python main.py setup` pide el código por `input()`, y en un contenedor no hay consola: Telethon manda el código, se encuentra con un EOF y el backend arranca con un cliente **conectado pero sin autenticar**. A partir de ahí todo lo de Telegram falla con `The key is not registered in the system` (AuthKeyUnregisteredError) y la indexación estima 0 mensajes sin más explicación. Por eso existe la pestaña **Telegram** del panel de admin: parte el diálogo en `POST /api/admin/telegram/send-code` y `POST .../sign-in`, reutilizando el mismo cliente de Telethon que ya tiene el backend (el `phone_code_hash` vive en memoria entre las dos peticiones). Al terminar resuelve los canales y arranca la indexación, así que no hace falta reiniciar. La verificación en dos pasos devuelve **428** y el formulario pide entonces la contraseña.
- **Si Telegram se desconecta, se reconecta solo** (`TelegramDownloader.vigilar_conexion()`, cada 30 s). Telethon reconecta tras un corte corto, pero **no** si el primer `connect()` falla ni cuando agota sus reintentos: el cliente se queda desconectado para siempre. Pasó tras un reinicio del servidor: 16 horas en que todo «Ver» de algo no descargado daba 500 («El servidor no ha podido comprobarlo»; en el log, `Cannot send requests while disconnected`), no se indexaba nada nuevo y la pestaña Telegram decía «autorizado» con **0 canales resueltos** — ese par es la señal. Al reconectar se resuelven los canales que falten; con la conexión viva, un canal sin resolver se reintenta cada 10 minutos. Mientras dura un corte, `/api/reproducir` contesta «Telegram no está conectado ahora mismo» y no lo guarda. Probado en `backend/tests/prueba_vigilar_telegram.py` (necesita telethon: en local no está en el venv, se corre en la imagen del backend).
- **`TelegramDownloader.start()` no inicia sesión**: solo hace `connect()` y comprueba `is_user_authorized()`. Antes llamaba a `client.start(phone=...)`, que en un contenedor pedía el código por consola, moría con un EOF y **gastaba un envío de código en cada arranque**; con varios redespliegues seguidos Telegram acababa devolviendo `SendCodeUnavailableError`, y el hash que dejaba cacheado convertía la siguiente petición del panel en un reenvío. El alta de sesión vive solo en la pestaña Telegram del panel (y en `python main.py setup`, que sí tiene consola).
- **El código de Telegram y su `phone_code_hash`**: Telegram exige las dos cosas juntas en `auth.signIn`, así que el hash se guarda en `app_settings` (`telegram_pending_*`). Cuando vivía solo en memoria, cualquier redespliegue dejaba tirado al usuario: el código llegaba al móvil y ya no había con qué canjearlo. Ojo tambien con `send_code_request()`: Telethon cachea el hash en `client._phone_code_hash` y, **si lo tiene, no manda un código nuevo sino un `ResendCodeRequest`**; pulsando el botón un par de veces se agotan las vías (SMS, llamada) y Telegram responde `SendCodeUnavailableError`. Por eso se hace `pop()` del hash cacheado antes de pedirlo. El código llega como mensaje dentro de la app de Telegram, no por SMS, si hay sesión abierta en otro dispositivo.
- **`app_settings` manda sobre el `.env`**: el API ID, el API Hash y el teléfono se editan desde la pestaña Telegram (`POST /api/admin/telegram/credentials`) y se guardan en la tabla `app_settings`, no en el `.env`: en Coolify el `.env` lo regenera la plataforma en cada redespliegue y lo escrito ahí se perdería. `apply_saved_settings()` los vuelca sobre `config` al arrancar, después del pool y **antes** de construir el `TelegramDownloader` (que se queda con una copia de los tres valores, así que al cambiarlos hay que actualizar también `downloader.api_id/api_hash/phone`). Cambiar de aplicación de Telegram invalida la sesión: el fichero se aparta como `user.session.bak-<epoch>` en vez de borrarse.
- **Despliegue automático al hacer push**: el webhook que la GitHub App de Coolify crea por su cuenta **no puede funcionar aquí**. Apunta a `http://80.29.131.182:8000` y ese puerto está cerrado (Coolify vive en el homelab, dentro de la tailnet); por eso durante mucho tiempo todos los despliegues del historial decían «Manual» aunque *Auto deploy* estuviera activado. La solución no es abrir el puerto, es invertir la dirección: `.github/workflows/desplegar.yml` hace que **el runner de GitHub entre en la tailnet** (`tailscale/github-action`, `tag:ci`) y llame a la API por la IP privada `100.97.138.49:8000`. Nada queda expuesto. La lógica está en `desplegar.py` y no en una tubería de curl porque hay que distinguir tres cosas: que el despliegue no se pueda **pedir** (fallo), que acabe **mal** (fallo) y que no se pueda **consultar** su estado (no es fallo: ya está en marcha). Busca las claves del JSON donde estén, porque la forma de la respuesta de Coolify cambia entre versiones y la instancia no publica su especificación. El alta (token de Coolify, cliente OAuth de Tailscale, ACL y secretos) está en `.github/workflows/README.md`. Dos cosas que costaron un intento cada una: la **API de Coolify viene desactivada** (Settings → Advanced), y el token necesita **`Deploy` y `Read` marcados los dos** — con `Deploy` a secas la API devuelve `403 You are not allowed to access the API` aunque el token se autentique bien, porque la guarda general exige `read`.
- **Coolify**: se despliega con `docker-compose.coolify.yml` (ver `DEPLOY-COOLIFY.md`), no con el de la raiz. Sin `db`, sin `ports:` (el 80 es del proxy de Coolify y el bind fallido deja el contenedor reiniciando), con healthchecks propios (el de Coolify usa `curl`, que no esta en nginx:alpine ni en python:slim) y "Connect To Predefined Network" activado para que resuelva el hostname del PostgreSQL externo.
- **Buscador: la URL no manda sobre el input**. `Search.tsx` (web) escribe el término en la URL con `setParams` en cada búsqueda, y un `useEffect` sobre `q` lo devolvía al campo de texto: si seguías escribiendo mientras la petición estaba en vuelo, al llegar la respuesta el input daba un salto atrás al término viejo. Ahora un `ref` recuerda lo último que escribimos nosotros en la URL y solo se sincroniza cuando el cambio viene de fuera. Las tres apps llevan además un contador de petición: una respuesta atrasada no pisa los resultados de lo que se está escribiendo.
- **Entrar en la tele con el móvil (QR)**. Teclear usuario y contraseña con las flechas del mando era lo más tedioso de la app, así que la pantalla de entrada de la tele (Samsung, LG, Fire TV y PS4) enseña **primero un QR**: se escanea con el móvil, se confirma y la tele entra sola, como en Netflix o YouTube. Hay **dos códigos y no son intercambiables**: el `codigo` de seis letras es el que se ve (en el QR y escrito debajo) y **no da acceso a nada**, solo se puede *aprobar* desde una cuenta abierta; el `secreto` solo lo conoce la tele y es con lo que pregunta (`/poll`) y recoge los tokens, **una sola vez**. Todo caduca a los 5 minutos y la tele pide otro sola, porque puede quedarse horas en esa pantalla. Vive **en memoria** (`services/vincular.py`): es efímero, el backend es un solo proceso y si se reinicia la tele pide otro código; si algún día hay varios workers, tiene que pasar a Redis. Cuatro detalles. **El QR apunta al dominio y no a la IP** (`TMD_PUBLIC_URL`): la tele habla con el servidor por la IP de casa, pero la sesión del móvil está en el dominio, y con datos la IP no llega. **iOS abre los QR en Safari**, que no comparte sesión con la app instalada, así que se llega muchas veces sin sesión: el login del móvil recuerda a dónde se iba (`state.despues`) y vuelve a la confirmación; y para quien use la app instalada, Perfil → «Vincular una tele» pide el código escrito. **Siempre se confirma**, aunque se llegue del QR, diciendo en qué aparato: aprobar mete en tu cuenta a quien tenga esa pantalla delante, y un QR te lo puede haber puesto delante otro. Y `/poll` contesta **siempre 200** (también caducado): un 401 haría que `apiFetch` de la tele la mandara al login, que es donde ya está. Probado en `backend/tests/prueba_vincular.py`.
- **Las teles prueban la IP de casa y, si no contesta, el dominio**. Los paquetes llevan `VITE_API_BASE` (la IP, para que las películas no salgan a internet) y `VITE_API_BASE_RESPALDO` (el dominio); `main.tsx` busca `/tv/` en la primera con 1,5 s y en la segunda con 3 s, y en el Fire TV lo mismo hace `MainActivity.cargarInterfaz()` antes de cargar nada. Existe porque **el DHCP de casa mueve la IP del servidor** y cada vez dejaba todas las teles sin servidor hasta recompilar. La copia empaquetada ya no fija la dirección al compilar: `usarServidor()` en `services/api.ts` la pone al arrancar (y `ws.ts` la lee de ahí). Ojo: la IP y el dominio son **dos orígenes** y la sesión se guarda por origen, así que si una tele pasa de uno a otro hay que volver a entrar (con el QR es un momento).
- **Contraseña provisional: se cambia al entrar** (`users.must_change_password`). La que pone el admin al **crear** una cuenta o al **restablecer** la de otro la conoce él, así que queda provisional (la suya propia desde el panel no); la cuenta `admin` de una instalación nueva con la contraseña por defecto, también. Las cuentas que ya existían quedan en `FALSE`. **Lo impone el servidor, no las apps**: el login (y `/refresh`, que mira la base de datos y no copia el token viejo) emite un access token con `cambiar: true`, y con él `get_current_user` contesta **403** (`CAMBIAR_PASSWORD`; 403 y no 401, porque renovar daría otro igual), `get_stream_user` y el WebSocket lo rechazan, y solo `/auth/me` y `/auth/password` lo aceptan (`get_user_pendiente`). `/auth/password` con la provisional no pide la actual (se acaba de escribir), no admite la misma y **devuelve tokens nuevos**. Las tres apps enseñan `CambiarPassword` en vez de cualquier otra pantalla; mientras tanto la sesión **no cuenta como abierta** (`isAuthenticated` en web y tele, `me` en el móvil, con `mustChangePassword`/`pendiente` aparte) para que favoritos, descargas y demás no se carguen a base de 403. En el panel de usuarios sale «contraseña provisional» hasta que la cambia. Probado en `backend/tests/prueba_cambiar_password.py`.
- **Última conexión y «en línea»** (`services/presencia.py`). Las dependencias de `auth/dependencies.py` apuntan en un diccionario la hora de cada petición con token —también cada tramo de vídeo con la entrada de reproducción y el WebSocket; no las del usuario `sistema`— y **una vez por minuto** se vuelca a `users.last_seen_at` (y al apagar): escribir en cada petición sería una escritura por tramo de vídeo. La lista de Admin → Usuarios toma lo más nuevo de la memoria y la base de datos, **«en línea» es haber hecho algo en los últimos 5 minutos**, y el panel vuelve a preguntar cada 30 s; el Resumen cuenta cuántos hay. No hay historial anterior a esto: hasta que alguien vuelve a usar la app sale «Sin conexiones registradas». Probado en `backend/tests/prueba_presencia.py`.
- **«Recuérdame»**: marcado, los tokens van a `localStorage` y la sesión aguanta cerrar el navegador (o la app de la tele); sin marcar van a `sessionStorage` y se pierden al cerrar. `setTokens(access, refresh, remember?)` solo decide cuando se le pasa el tercer argumento — al renovar el token se respeta lo elegido al entrar, y de dónde salieron los tokens al arrancar es lo que dice qué se eligió, así que la decisión sobrevive a recargar la página.
- **Onboarding: está en las tres apps y el mínimo se adapta**. Exigía 3 películas **y 3 series** fijas; si el catálogo ofrecía menos de 3 de un tipo, el botón de guardar se quedaba apagado para siempre, no se podía terminar y al volver a entrar lo pedía otra vez (es lo que le pasaba a un usuario). Ahora el mínimo es `min(3, lo que hay)`, y con el catálogo vacío del todo se ofrece entrar guardando preferencias vacías, que es lo que marca el onboarding como hecho. **Antes solo existía en la web**: quien entrara por el móvil o la tele no tenía forma de guardar sus gustos. `POST /api/preferences` consulta TMDB en paralelo y con una sola `ClientSession`: antes era un bucle secuencial de hasta 20 llamadas de 10 s cada una, abriendo sesión nueva en cada vuelta. Si `GET /api/preferences` falla, los tres clientes asumen que **sí** hay preferencias: es peor encerrar a alguien en el onboarding por un fallo de red que no personalizar la portada.
- **La web de escritorio también es instalable**: no tenía `manifest.webmanifest` ni las metas de Apple, así que al añadirla a la pantalla de inicio de un iPad no había ámbito definido y cualquier navegación se tomaba como salida de la app: iOS abría encima la barra de direcciones de Safari con las pestañas. Con `scope: "/"` toda la web queda dentro. Ojo: en iPad el *user agent* es de escritorio y la pantalla mide más de 768, así que el redirector de `index.html` **no** lo manda a `/m/` — un iPad usa la web, no la PWA de móvil.
- **Móvil, barra de pestañas: el hueco de abajo en Safari no es un fallo**. Desde iOS 15 la barra de direcciones de Safari vive abajo y, al desplazar, se encoge a una pastilla translúcida que **sigue ocupando sitio**. `visualViewport.height` la descuenta bien, el armazón acaba justo encima y la página **no puede pintar ahí**: ningún CSS lo arregla, la única salida es usar la app instalada en la pantalla de inicio. Lo que sí se hace es que el lienzo (`html`/`body`) vaya del color de la barra (`#0A0A0A`) y el fondo de la app lo ponga `.app-shell`, así lo que asoma es del mismo color y la barra parece llegar al borde. Un `body::after` para eso **no sirve**: se probó y en Safari no pinta (el fondo del `body` se propaga al lienzo y se come el pseudo-elemento con `z-index: -1`).
  Instalada es otra historia y **no se mide nada**: `main.tsx` pone la clase `instalada` en el `<html>` y el CSS ancla el armazón con `top: 0; bottom: 0; height: auto`. Medido quedaba corto: en un iPhone 16 Pro la pantalla son **874** px CSS y `window.innerHeight` dice **812**, porque descuenta la franja del reloj **de arriba** — pero con `viewport-fit=cover` la página pinta de borde a borde, así que el armazón empezaba en y=0, acababa en 812 y la barra de pestañas se iba con él, dejando los iconos a ~105 px del canto cuando deberían estar a 34. Con `bottom: 0` el borde es el real y el `padding-bottom: var(--safe-b)` de la barra hace lo único que le toca: levantar los iconos por encima del indicador de inicio. **Antes de volver a tocar esto, mira Admin → Ajustes → Pantalla en el teléfono**: enseña el modo, los dos altos y las variables. Existe porque este hueco costó cuatro diagnósticos a ciegas, y los números lo resolvieron en uno.
- **Buscador en el onboarding**: `GET /api/onboarding/picks?q=` busca por título en `tmdb_cache` y **suelta los filtros de nota y año** (sin `q` salen los **más conocidos desde 2010**, por votos de TMDB y con carátula: se ordenaba por nota a secas y salían primero cortos con dos votos y un 10; buscando, si alguien pide una peli concreta la quiere aunque sea de 1980). Dos cuidados: `DISTINCT ON` obliga a ordenar por su propia clave, así que la relevancia se ordena en una consulta **de fuera**, donde la columna ya se llama `tmdb_title`; y el mínimo exigible se mide sobre el catálogo sin filtrar (`disponibles`), no sobre los resultados — si no, buscando una sola película el mínimo bajaba a una y se podía terminar el onboarding con un solo gusto marcado. La barra de botones del móvil se muestra también cuando hay selección aunque la búsqueda no devuelva nada, o se perdía el «Siguiente».
- **Pantalla de espera al reproducir en el móvil**: el `<video controls>` se veía en línea con sus propios controles mientras cargaba y solo al empezar a reproducir saltaba `webkitEnterFullscreen()`, de modo que parecían dos reproductores peleándose. Ahora se tapa con una espera (fondo del título + carátula + «Preparando el vídeo…») que se retira 120 ms después de entrar en pantalla completa. Lleva red de seguridad: a los 20 s, o si el `<video>` da `error`, se retira igualmente — más vale ver el reproductor que quedarse en una espera eterna.
- **En el movil, una serie en Descargas lleva a su ficha, no se despliega**. Era un acordeon dentro de la lista y habia que desplegar, mirar y volver a plegar para pasar de una serie a otra; ademas desde ahi no se podian bajar los episodios que faltaban. Ahora la fila enlaza a `/m/t/series/:tmdbId`, que es la pantalla con **todos** los episodios. El id sale de `/api/metadata/batch`, que ya devolvia `tmdb_id` y `media_type` (en TMDB el tipo es `tv`, no `series`: hay que traducirlo). Si TMDB no conoce el titulo no hay ficha, y entonces la fila reproduce el primer episodio en vez de quedarse muerta. En escritorio se queda el acordeon: ahi la pantalla es ancha y no estorba.
- **El progreso de descarga en el movil hay que volver a pedirlo**. El telefono suspende el WebSocket en cuanto se apaga la pantalla o se cambia de app, y el sondeo de `/status` solo corria si ya se sabia que habia algo bajando: al volver, la barra estaba congelada o no estaba. `LibraryContext` vuelve a conectar y relee en `visibilitychange`/`focus`, y `Downloads` llama a `loadStatus()` al montarse.
- **Volver atrás no puede recargar la portada**. En el móvil `<main>` llevaba `key={location.pathname}`, así que **cada navegación lo desmontaba**: entrar en una película y volver dejaba la portada recién montada, arriba del todo, y había que bajar otra vez hasta donde estabas. Ahora el armazón es siempre el mismo y el scroll lo decide el tipo de navegación (`useNavigationType`): hacia delante se empieza arriba y al volver se recupera lo que tenía **esa entrada del historial** (`location.key`, no la ruta: dos visitas a la portada son dos sitios distintos). Y no bastaba con el scroll: la portada se volvía a pedir al montarse y, como el orden lo decide una semilla aleatoria, volvía **otro catálogo** y nada estaba donde se dejó. Las filas viven ahora en un módulo (`useCarriles`), con su semilla, sus páginas ya cargadas y el scroll de cada carril; se repiden a los 10 minutos. **La posición se anota en cada evento de scroll y en ningún otro sitio**, y esto no es un detalle: anotarla también «al salir», en la limpieza del efecto, es lo que tuvo el arreglo roto medio día. React corre los `useLayoutEffect` (donde se pone el scroll a 0 al entrar en la ficha) **antes** que las limpiezas de los `useEffect`, así que ese último guardado escribía encima el 0 que acababa de poner el otro efecto y al volver se restauraba siempre el principio — exactamente el síntoma que se venía a arreglar. Y la restauración **insiste** (hasta 20 intentos de 50 ms, rindiéndose en cuanto el dedo toca la pantalla): si se vuelve pasados los 10 minutos la portada llega por red, y hasta que llega la página es más corta que la posición buscada y el navegador recorta el scroll a lo que hay. En la web el problema era otro: la ficha era un modal sin URL, así que «atrás» salía de la portada. Ahora la ficha **vive en la URL** (`?ficha=s1234`), con lo que atrás la cierra y además el aviso de un episodio puede abrir el título con un enlace.
- **Carriles de género paginados: el orden tiene que ser reproducible**. Se cargan de veinte en veinte al acercarse al final, y ahí está el problema: con `ORDER BY RANDOM()` la página 2 no continúa a la 1, repite y se salta títulos. La clave de orden es un **hash determinista** (`md5(semilla || tmdb_id || tipo)`) elevado a `1/peso` igual que el muestreo ponderado de siempre, así que el orden es estable para una semilla y distinto en cada sesión; `/browse/home` devuelve la semilla y `/browse/genre` la recibe. Dos detalles del SQL: el hash va de **48 bits** (`bit(48)::bigint`) porque con `bit(32)` Postgres devuelve enteros **con signo** y la mitad de las claves salían negativas (tanto como no ponderar), y los parámetros llevan cast explícito (`$1::text`, `$3::int`) o Postgres contesta «operator is not unique». La fila no crece sin fin: es una **ventana** de 80 tarjetas que suelta por la izquierda al añadir por la derecha (y vuelve a pedirlas si se desliza hacia atrás). Al soltarlas todo se desplaza, así que el carril corrige su `scrollLeft` con el número de tarjetas que se han ido (`shift`) por el paso de una tarjeta, medido de las dos primeras; **y hay que quitar `scroll-behavior: smooth` mientras se corrige**, o la corrección se anima y se ve como un salto.
- **El orden de la portada es la nota, ponderada**. Lo que se pidió fue «de la valoración más alta a la más baja, pero que no salga siempre lo mismo», que suena contradictorio y no lo es: el peso del muestreo (`clave = u^(1/peso)`, Efraimidis-Spirakis) pasa de ser la antigüedad del título a ser su nota. Con `(nota - 4)^4` un 8,5 va antes que un 6 el 96 % de las veces, pero dos notas parecidas se barajan entre sí. Medido sobre 2.000 títulos con notas realistas: la nota media del carril sube de 6,4 a 8,0, menos de un título por debajo de 6,5 entra en las diez primeras tarjetas y entre dos visitas no se repite casi ninguna. Tres cuidados. **`rating` a secas no sirve**: ordenar por él da los títulos con cuatro votos (un estreno recién subido tiene un 10 con dos votos), así que la nota es una media bayesiana con 50 votos de referencia. **`vote_count` se añadió después**, así que las fichas antiguas lo tienen a NULL: NULL no es «cero votos» sino «no se sabe», y a esas se les hace caso a su nota tal cual, porque tratarlas como cero las hundiría todas a la media. Y el peso se recorta a [0,5 – 1000] porque el exponente es `1/peso`: con pesos diminutos Postgres acaba elevando un número muy pequeño a 1.000, que es donde `numeric` empieza a dar problemas. Efecto secundario asumido: los carriles de género ya no priorizan lo reciente, así que saldrán clásicos bien valorados. «Añadido recientemente» y «Mis favoritos» siguen siendo cronológicas, que es lo que significan.
- **«Ya me la he visto» es del título, no del archivo**. Vive en `user_watched` y no en `playback_progress` porque eso va por **ruta de disco**: marcar una película que no está descargada tiene que valer igual, y marcar un episodio no puede depender de tenerlo. `season = 0, episode = 0` significa el título entero (la película, o la serie completa) y se usan ceros en vez de NULL para que la clave primaria y el `ON CONFLICT` sean directos. Quitar el visto del título entero borra también el de sus episodios: «serie no vista» con ocho capítulos marcados no es un estado que la ficha sepa pintar. Pero **quitar el visto de un capítulo de una serie marcada entera no es eso**: la serie deja de estar entera y el resto sigue visto. Antes se resolvía quitando el título entero y se perdía todo lo marcado; ahora `POST /api/watched/episodios` marca de golpe todos los capítulos que conoce la ficha menos ese, con `quitar_entero` (que borra solo la fila del título, no los capítulos), en una transacción. El mismo endpoint es el **visto por temporada** de la ficha (web y móvil). Lo que se marca hace tres cosas, y las tres importan: pinta el visto en la ficha, **saca el título de «Continuar viendo»** (decir «ya me la he visto» y seguir viéndola en la portada es contradictorio) y **mueve las recomendaciones**. Está en las tres apps: en la tele (`tizen/src/hooks/useWatched.ts`, el mismo hook con `recargar()`, porque el reproductor se abre encima de la ficha sin desmontarla y al cerrarlo lo marcado en los créditos tiene que verse) hay un botón «Marcar vista» junto a Favorito, una casilla «Visto» al final de cada fila de episodio y un botón por temporada bajo las pestañas de temporadas.
- **Al empezar los créditos, lo visto se da por visto** (`POST /api/progress/creditos`, lo llama `useSiguiente` una vez por archivo al llegar a `momentoDeAviso()`: los créditos si se saben, y si no 45 s antes del final). Es cuando la gente deja de mirar, y esperar al `ended` o al 95 % dejaba el capítulo a medias si se cerraba en los créditos. El servidor deja el progreso **terminado** (de una serie, «Continuar viendo» ofrece el siguiente desde el principio) y **marca visto** en `user_watched` el capítulo —con eso, completa la temporada, la ficha la pinta vista— o la película entera, que sale de «Continuar viendo»; las dos cosas suman a las recomendaciones. Un capítulo marcado cuenta como terminado en «Continuar viendo» aunque su posición diga otra cosa (`marcado` en `continuar.py`): tras el aviso el reproductor sigue guardando cada pocos segundos, y unos créditos de más del 5 % lo dejaban «a medias» otra vez.
- **El capítulo siguiente de «Continuar viendo» sale también del catálogo**, no solo del disco: `progress_router._episodios_en_catalogo()` busca, de cada serie del historial, los episodios que se pueden ver sin descargar (extensión o `interior`), con el enlace del canal en el que se iba viendo si lo hay. Por eso una serie al día desaparece de la fila al ver el último capítulo y **vuelve sola en cuanto llega el nuevo**: la fila se calcula en cada visita con lo que haya entonces. Lo descargado manda sobre el catálogo.
- **Si el vídeo no llega a arrancar, se vuelve a pedir solo** (`hooks/useReintento.ts`, el mismo en las tres apps): hasta cuatro veces en ~17 s, con `&intento=N` en la URL para que el `<video>` o hls.js la pidan de nuevo, y volviendo al punto si ya se había saltado. Pasaba al pulsar «Siguiente episodio» viendo sin descargar y había que salir y entrar. En hls.js era peor: ante un fallo de la **lista inicial** se llamaba a `startLoad()`, que no la vuelve a pedir, así que la pantalla se quedaba en negro para siempre; ahora esos errores (`MANIFEST_LOAD_ERROR`, `_TIMEOUT`, `PARSING_ERROR`) pasan por el reintento. La consulta de pistas (`modoDeReproduccion`) reintenta también tres veces: si fallaba se abría el archivo tal cual, que con AC-3 en Chrome es verlo mudo. Mientras quedan intentos, ningún reproductor avisa del error.
- **Las recomendaciones se mueven con lo que se ve**. Los pesos por género ya no son solo los del onboarding: `_gustos_de()` les suma los géneros de lo que la cuenta ha visto —lo marcado a mano y lo reproducido pasada la mitad, que también dice lo que le gusta a alguien—, y las dos cosas están en la misma escala (cuántos títulos de cada género), así que se suman sin normalizar nada: con seis elegidos al entrar y veinte vistos después, lo visto pesa más. Por eso la fila cambia poco a poco sin que nadie tenga que volver a pasar por el onboarding, y no hace falta ninguna tarea de fondo: se calcula al pedir la portada. Lo visto entero además **se excluye** de la fila: recomendar algo que alguien acaba de terminar es ruido y le quita el sitio a lo que no conoce. Ojo al escribir ese SQL: `duration > 0 AND position / duration >= 0.5` parece seguro y no lo es, porque Postgres puede evaluar las condiciones en el orden que quiera y una división por cero es un **error**, no un NULL; va como `position >= duration * 0.5`.
- **«Recomendado para ti» va por épocas, no por año**. Se pidió «de lo actual a lo más viejo, mezclando como mucho quince años: 2026 y 2011 juntos, y luego hacia abajo». Ordenar por año a secas daría una escalera (todo 2026, después todo 2025…) donde dos películas de 2014 y 2012 no se cruzan nunca; por eso el orden es por **bloques de 16 años distintos** (15 de diferencia como mucho): primero 2026-2011 mezclado por dentro, luego 2010-1995, y así. Dentro de cada bloque manda la nota ponderada con la clave de la semilla, así que sigue rotando y sigue paginando. Los títulos sin año caen en un bloque lejano y salen al final, que es lo que toca con algo que no se sabe de cuándo es. La puntuación por gustos decide **qué** entra en la fila; las épocas, en qué orden.
- **Paginan las cuatro filas, no solo los géneros**. Que una fila se acabe a las veinte tarjetas y la de al lado no, se nota. Novedades, «Añadido recientemente», «Recomendado para ti» y «Mis favoritos» van por la misma puerta (`/browse/row?key=…`) y cada una viaja con su `total`. Lo que costaba era el orden: **con `RANDOM()` la página 2 no continúa a la 1**, repite títulos y se salta otros, así que todas las filas aleatorias ordenan por la clave determinista de la semilla. Dos consecuencias buenas de paso: «Recomendado para ti» **se puntúa ahora en SQL sobre el catálogo entero** (antes se puntuaba en Python sobre una muestra aleatoria de 800, o sea que las «mejores recomendaciones» eran las mejores *de una muestra al azar*), y la muestra grande solo se pide si alguna consulta falla, así que la portada hace menos trabajo que antes. Ojo con `get_estrenos`: se llama así y no `get_novedades` porque eso ya existe en `connection.py` para el registro de lo que llega en vivo a los canales, que es otra cosa.
- **«Novedades» mira los meses, no el año**. Siempre salían las mismas películas: se ordenaba por `year` y, con 2026 entero empatado, el desempate (votos, nota) era el mismo en cada visita. `tmdb_cache` solo guardaba el año porque era lo único que se mostraba, así que se ha añadido `release_date` y el orden es un muestreo aleatorio ponderado por **días** (peso 31 para lo estrenado hoy, 1 al borde de la ventana de 24 meses): rota en cada visita pero siempre con lo más reciente. Dos cuidados. Lo que ya estaba en cache no tiene fecha, de modo que `services/estrenos.py` la rellena **solo de los últimos años** (lo único que puede entrar en la fila: son cientos de consultas en vez de veinte mil) y mientras tanto se usa el 1 de enero de su año, que es la precisión que había antes; si la ventana da pocos títulos, la fila se completa con el criterio viejo para no quedarse corta. Y **en el frontal no se escribe ningún mes**: la fecha es para ordenar, no para mostrarse (en las tarjetas sigue saliendo el año).
- **Seguimiento de series y avisos al móvil**. Seguir una serie es pedir que avisen de los episodios nuevos, y se activa de dos maneras: la campana de la ficha y **haber visto un episodio** (`progress_router` llama a `auto_follow`). Por eso la fila de `series_follows` **no se borra** al dejar de seguir, se queda con `active = false`: sin esa marca, la serie que alguien quitó volvería a seguirse en cuanto reprodujera un capítulo. El aviso **no se manda cuando llega el archivo**: en ese momento todavía no se sabe de qué serie es (el emparejamiento con TMDB va en otro bucle, segundos o minutos después) y sin `tmdb_id` no hay a quién avisar; lo hace un vigilante cada 10 minutos (`TMD_AVISOS_MINUTOS`) sobre lo indexado *que ya tiene ficha*, con **6 horas de solape** por si el emparejamiento se retrasó. Tres reglas contra el spam, que es lo único que acaba en «silenciar esta app»: solo lo que llegó **después** de empezar a seguir (si no, seguir «Suits» hoy traería 134 avisos), **un aviso por serie** aunque lleguen ocho episodios, y lo ya avisado no se repite (`series_avisos`: lo que hace nuevo a un episodio no es su fecha, es que esta cuenta no lo sabe). La primera pasada **no avisa de nada**: deja la marca de tiempo y espera, porque en un servidor recién indexado «lo nuevo» son 160.000 archivos.
- **Las claves VAPID viven en `app_settings`, no en el `.env`**. La pública queda grabada dentro de cada suscripción del navegador: si cambia, **todas** dejan de valer de golpe y nadie recibe nada hasta volver a dar permiso. En Coolify el `.env` lo regenera la plataforma en cada redespliegue, así que ahí se habrían perdido. Se generan solas la primera vez (P-256; la privada se guarda como el escalar en crudo en base64url, que es lo que `pywebpush` acepta sin tocar archivos). Enviar es **bloqueante** (`pywebpush` va con `requests`), así que cada envío pasa por un hilo. Y lo que el servicio de push responda importa: **404/410 significa que la suscripción está muerta** (app desinstalada, datos borrados) y se borra la fila; otro error solo cuenta, y a las cinco se deja de intentar.
- **En el iPhone los avisos solo llegan con la app instalada**. Es condición de Apple (iOS 16.4+): en Safari a secas `PushManager` no existe, y el permiso se pide con el dedo del usuario, nunca al cargar. Por eso el interruptor está en el perfil y, cuando no se puede, dice **por qué** en vez de quedarse apagado sin explicación. La web de escritorio también los admite: se le ha añadido un `sw.js` que **no cachea nada** (solo los manejadores de `push` y `notificationclick`), porque meter una caché ahí solo pegaría versiones viejas en el navegador.
- **`apiFetch` ya pone `/api`**. Los tres `progress.ts` pedían `/api/progress` a través de él, o sea `/api/api/progress`: un 404 que los `try/catch` se tragaban, así que «Continuar viendo» **nunca llegó al servidor** y todo se quedaba en la caché del navegador (parecía funcionar porque la caché pinta la fila). Al tocar estos archivos, las rutas van sin prefijo.
- **La caché (Redis) no puede ser obligatoria**. Lo que tardaba no era la red, era recalcular lo mismo en cada visita: la portada agrupa `media_items` (250.000 filas) por título en **cada** consulta de **cada** fila, la ficha de un título recorre **la biblioteca entera en disco** para saber qué está descargado (un `os.walk` por carátula que se toca), `/media/tracks` lanza un `ffprobe` por reproductor que se abre y el buscador dispara una consulta por tecla. Todo eso va ahora por `services/cache.py`, con un espacio por tipo de dato y su caducidad (`portada`/`fila` 5 min, `ficha`/`disco`/`nombres` 10 min, `pistas` un día, `busqueda` 1 min). Tres reglas. **Si Redis no está o se cae, no pasa nada**: `iniciar()` deja la caché desactivada y `recordar()` calcula siempre, porque una caché que tumba la aplicación cuando se cae es peor que no tenerla. **Nada de una cuenta se guarda sin su id en la clave** (`mc:<espacio>:<cuenta>:<...>`): es el mismo error que ya se cometió dos veces en el navegador, y aquí enseñaría los favoritos de uno a todos los demás, así que `clave()` **no deja** construir una entrada de un espacio personal sin cuenta. Y **se invalida por prefijo, en segundo plano**: al acabar una descarga no se sabe qué fichas la mencionaban, así que se olvida el espacio entero (`cache.cambio_en_disco()`), y el barrido va con SCAN y sin esperarlo, porque invalidar no debe frenar a quien lo provoca. Un `None` nunca se guarda: cachear un fallo lo deja pegado todo el TTL. El estado (tasa de acierto, entradas, memoria) está en **Admin → Ajustes → Caché**, con botón de vaciar, porque una caché es invisible cuando va bien y también cuando no va.
- **Para que la portada se pueda cachear, la semilla ya no es aleatoria**. Era una por sesión, así que la clave era distinta en cada visita de cada cuenta y no se acertaba nunca — justo en la primera carga, que es la que se nota. Ahora quien no trae semilla recibe **la de la ventana de media hora** en la que esté (`VENTANA_SEMILLA_MIN` en `browse_router.py`): sigue rotando sola, solo que cada media hora en vez de en cada recarga, y quien ya tiene semilla (está paginando) la manda y se le respeta. Efecto visible: recargar dos veces seguidas da la misma portada.
- **Créditos: se guardan como «segundos antes del final», no como un minuto** (`services/creditos.py`). Dos enlaces de la misma película no duran lo mismo (un logo delante, una copia europea un 4 % más rápida), pero el final sí se mantiene, así que basta con medir **un enlace por película y uno por temporada**: el resto se predice (`prevision()`: duración del enlace − segundos de la referencia). Dos tablas: `creditos` (referencia por `tmdb_id`/tipo/temporada; temporada 0 = la serie entera, que se usa si la temporada no tiene la suya) y `creditos_enlace` (lo medido en un archivo, por su ruta como en `playback_progress`; manda sobre la previsión; `no_encaja` = se comprobó que ese enlace no sigue a su título y no se le predice nada). Las fuentes tienen prioridad y una floja no pisa a una fuerte: `manual` > `capitulos` > `imagen`. **Los capítulos salen gratis**: `leer_pistas()` lee también `-show_chapters` en la misma pasada de ffprobe y `recoger_capitulos()` apunta el inicio si hay un capítulo «Credits», «Créditos», «Ending», «ED»… en el 40 % final (un «Opening Credits» no cuenta). Medido sobre una muestra del catálogo, los traen ~9 % de las series y ~2,5 % de las películas; el resto vendrá del análisis de imagen, que está por hacer. Que un archivo **no** traiga capítulos no dice nada de sus créditos, así que entonces no se escribe nada. El reproductor pregunta `GET /api/creditos?path=&duracion=` y recibe `{inicio, origen: medido|previsto|null}`; con `null` sigue con su regla fija de 45 s. Probado en `backend/tests/prueba_creditos.py`.
- **Créditos por imagen, sin bajarse el final** (`services/analisis_creditos.py`). Un vídeo guarda una imagen completa (fotograma clave) cada pocos segundos; para saber si hay créditos basta con esas, así que se lee el índice (las tablas del `moov` en MP4, las Cues en MKV), que dice en qué byte está cada una, y se piden **solo esos trozos** a Telegram con **bloques de 128 KB** y una caché de bloques (`lector_tg`; `reproduccion.leer()` acepta `bloque=`). Cada fotograma se decodifica **suelto** con ffmpeg (pegados en un flujo, ffmpeg toma varios IDR seguidos por la misma imagen) a 320×180 en gris y se clasifica: créditos (≥ 92 % negro con algo claro y bordes finos), negro o imagen. **Solo importa dónde empiezan**: lo de después (el logo de la productora, una escena) da igual; exigir que el tramo llegara hasta el final hizo fallar media temporada de *Breaking Bad*. Medido: *Breaking Bad* entera, 47 de 47 episodios con ~3 s de error y 169 MB de Telegram (referencias más comprobaciones); *Mass*, 25 MB y 16 s antes del capítulo «End Credits». Solo MP4/MKV con H.264 o HEVC: los AVI no (un XviD suelto necesita la cabecera delante). **Al cambiar el detector hay que subir `analisis_creditos.VERSION`**: lo medido por imagen con una versión anterior deja de contar como medido (`creditos_enlace.version`) y se recomprueba cuando alguien abre ese enlace. Pasó con *Animales* en MKV: en los créditos hay un fotograma clave cada ~10 s y una tarjeta con dos nombres salía como imagen, así que la versión 1 los dio por empezados siete minutos tarde; la 2 cuenta como créditos un fotograma ≥ 97 % negro con algo claro aunque apenas tenga bordes, y en la comprobación acepta dos fotogramas seguidos que abarquen 8 s. **El listado de nombres de las películas** (dos o tres columnas que suben llenando la pantalla) no lo reconocía nadie hasta la versión 4: a 320×180 tanta letra deja solo un 75-90 % oscuro y salía como «imagen», así que en la primera pasada **dos de cada tres películas** se quedaron sin resultado (X-Men 2) o con el último minuto como inicio (Aquaman, Matrix Revolutions: 1 min de créditos que eran 8). Lo que lo distingue es que **lo que no es negro (< 25) es casi todo borde** (`DENSIDAD_LETRAS`): medido en 20 películas, el listado da 0,6-0,8 bordes por píxel no negro y las escenas como mucho 0,24. Se ajustó con los fotogramas reales del final de 20 películas y 8 series bajados con la sesión de pruebas: 15 pasaron a medirse bien y ninguna serie cambió. Lo que sigue sin poder medirse: créditos **encima de una escena** (*Friends*, *Doce hombres sin piedad*: entonces queda la regla de 45 s) y los MP4 con vídeo **MPEG-4 Part 2** (`mp4v`, no analizables). **Al subir la versión, el arranque deja pendiente lo que dependía del detector** (`pasada_creditos._si_cambio_el_detector`, con la versión medida en `app_settings.creditos_detector`): borra las referencias de películas sacadas de la imagen y lo que se quedó sin resultado, y la pasada lo vuelve a coger; lo de capítulos, lo puesto a mano y las referencias de temporadas no se tocan. Probado con vídeos generados por ffmpeg en `backend/tests/prueba_analisis_creditos.py`.
- **MKV con un SeekHead que apunta a otro** (`mkv.cabecera`). Los que escribe libwebm —los «[x265]» de iZombie o The Expanse, en Las Cositas Ballin— llevan al principio un SeekHead que **solo dice dónde hay otro SeekHead al final**, y es ese el que apunta a las Cues. Leyendo solo el primero se daban por «MKV sin indice (Cues)»: temporadas enteras sin créditos y **sin HLS al vuelo**, aunque el índice estuviera. Se comprobó leyendo un 5x01 real por `/api/stream`: segundo SeekHead de 79 bytes a 65 KB del final y Cues justo donde dice. `cabecera()` sigue el puntero (dos saltos como mucho) y la usan el HLS y el análisis de créditos; `reproduccion.VERSION` pasó a 4 para volver a mirar el `hls` de lo ya comprobado. Probado en `backend/tests/prueba_mkv.py`, que fabrica uno así byte a byte.
- **Reintentar créditos sin volver a medir lo bueno** (`analisis_creditos.REINTENTO`). Subir `VERSION` borra las referencias de películas por imagen (~950, unos 24 GB de Telegram); para un cambio que **solo añade aciertos** se sube `REINTENTO`, y al arrancar `pasada_creditos` deja pendiente solo lo que falló (`sin_resultado` y las películas «ningun enlace legible»). La 1: el SeekHead anidado y una segunda pasada de `inicio_creditos` que, si la normal no encuentra nada, ignora la imagen de los últimos 12 s (el logo de la productora: con un fotograma clave cada 10 s, «CCN» se quedaba en el 67 %) y mide el mínimo hasta el final real del vídeo. Al ser solo un segundo intento, lo que ya salía no cambia.
- **El proceso de créditos** (`services/proceso_creditos.py`), por película y por temporada: primero se miran los enlaces uno a uno buscando un capítulo de créditos (los más probables antes: MKV, BluRay, WEB-DL); si ninguno lo trae, se mide la imagen del enlace **más ligero** (película) o de **tres episodios** sin el piloto, cuya **mediana** es la referencia de la temporada (los créditos de una serie cambian entre temporadas —35-44 s en *Breaking Bad*— pero casi nada dentro de una). Solo con `TMD_CREDITOS_ANALIZAR` encendido (apagado por defecto), lo dispara `GET /api/creditos` al abrir el reproductor: sin dato, el proceso del título o la temporada; con dato **previsto**, comprobarlo (±30 s, ~2-4 MB) y guardar el inicio medido. Va por **una cola de uno en uno**, porque la cuenta de Telegram la comparten el streaming y las descargas, y lo intentado queda en `creditos_proceso` para no repetirlo en cada apertura (lo que no se pudo medir se reintenta a los 30 días).
- **La pasada completa de créditos** (`services/pasada_creditos.py`, pestaña **Créditos** del panel en la web y el móvil): el mismo proceso de arriba recorriendo **todo** el catálogo de una vez —unas 6.000 películas y 5.500 temporadas con algún MKV/MP4, de la más votada a la menos, para que si se para a medias lo medido sea lo que más se ve—. Se **lanza y se pausa a mano** (`/api/admin/creditos/pasada`) y lanzada se apunta en `app_settings` (`creditos_pasada`): **sigue sola tras un reinicio o un despliegue**; pausada, no. **Va según entra**: cada 15 min (`REFRESCO_S`) vuelve a mirar qué películas y temporadas no tienen sus créditos y las mete en la cola (por votos), y al vaciarse la cola **no se para**: queda «al día» vigilando lo nuevo. Un capítulo nuevo de una temporada ya medida no necesita nada (se predice de la referencia de la temporada); lo que entra son los títulos y las temporadas nuevas, que mientras tanto tiran de la referencia general de la serie. Lo que se está midiendo se apunta en `_en_curso` para que el refresco no lo meta dos veces (aún no tiene fila en `creditos_proceso`). Va **de tres en tres** (`TAREAS`) pero cede: con una **descarga en marcha se para del todo** hasta que acabe (se pidió que las descargas tengan preferencia), y con **alguien viendo algo sin descargar sigue con una sola tarea**. Lo segundo lo dice `files_router.ultimo_tramo_visto`, el último tramo de Telegram servido a alguien que no es el usuario `sistema` (ffprobe mirando pistas o capítulos, que si contara haría que la pasada se cediera el paso a sí misma). No apunta nada propio para reanudarse: lo pendiente es lo que no tiene fila en `creditos_proceso`, y lo que falla por algo pasajero no se apunta y vuelve en la siguiente tanda. Es independiente de `TMD_CREDITOS_ANALIZAR`, que es lo de al ver. Probado en `backend/tests/prueba_pasada_creditos.py`.
- **«Siguiente episodio» también en streaming.** `que_viene()` solo entendía rutas de la biblioteca, así que con un enlace `tg:` devolvía «desconocido» y el reproductor no ofrecía nada al acabar un capítulo visto sin descargar. Ahora `_que_viene_streaming()` busca el episodio en el catálogo y devuelve el siguiente no marcado como visto, con el enlace **del mismo canal** si lo hay (suele ser el mismo ripeo) y, si no, el de tamaño más parecido. Con una película devuelve `kind: movie` con su `tmdb_id`, que es lo que necesita la pantalla del final.
- **El tráiler en la ficha** (`components/Trailer.tsx`, el mismo en las tres apps; `GET /api/media/{id}/trailer`). Se pidió que al abrir un título se viera la carátula y el tráiler apareciera **cuando ya estuviera cargado**, encima, así que el componente es invisible hasta que YouTube dice que está reproduciendo (y medio segundo más: los primeros fotogramas son negros), y al acabar se desvanece y vuelve la carátula, que nunca se ha ido de debajo. Los tráileres los da TMDB (`tmdb.trailer()`): de YouTube, trailer antes que teaser, oficial antes que de fans, el doblaje de España antes que el latino; **primero en español y si no en el idioma original** del título (no en inglés por defecto: se pidió así). Se cachea un día en el espacio `tmdb`, también el «no tiene». Se incrusta con la API oficial desde youtube-nocookie.com, sin controles, con `pointer-events: none` (es un fondo, no un reproductor) y **agrandado un 18 % sobre «cubrir»** para recortar el título y el logo que YouTube pinta en los bordes aunque no haya controles; el encaje se calcula a mano porque Chromium 53 (webOS 4) no tiene `ResizeObserver`. Se apaga (`activo`) mientras el reproductor está abierto encima de la ficha. **Sonido**: en la web y el móvil empieza en silencio con un botón de altavoz que solo sale mientras se ve (un navegador no deja arrancar un vídeo solo con sonido); **en la tele suena siempre y sin botón** (se pidió así), y si el aparato no deja arrancar con sonido, a los 3,5 s se arranca en silencio antes que quedarse sin tráiler. Si YouTube no carga (un aparato viejo, un vídeo retirado), se queda la carátula sin más. **También en el destacado de la portada** (`Hero` en la web y la tele, el de `Home` en el móvil), con las mismas reglas de sonido y parándose con lo que tape la portada: en la web, una ficha abierta (`?ficha=`), el reproductor o bajar hasta que el destacado ya no se ve (`IntersectionObserver`); en el móvil, el reproductor; en la tele, cualquier panel encima (ficha, reproductor, diálogo: `tv/tapado.ts`, porque van por portal y la portada sigue montada debajo; los avisos no cuentan). En la tele el destacado es la tarjeta enfocada, así que el tráiler solo arranca si el foco se queda **2,5 s** en ella (`REPOSO_MS`): pasar de largo por un carril no debe crear un reproductor de YouTube por tarjeta (en un Fire TV se notaría). Para eso `Featured` lleva `tmdbId`.
- **Títulos relacionados** (`GET /api/browse/relacionados`, para la pantalla del final del reproductor): primero lo que TMDB recomienda para ese título y tenemos en el catálogo, después lo que comparte más géneros, de mejor a peor nota; sin lo que la cuenta ha marcado como visto. No usa el CTE de la portada (agrupa los 250.000 archivos): filtra antes por candidatos. Cacheado una hora en el espacio `relacionados`, que no es de nadie: lo visto se quita después.
- **Al empezar los créditos, como Netflix** (`useSiguiente`, el mismo archivo en los tres clientes). El reproductor pregunta `/api/creditos` al empezar y, mientras no estén medidos, cada minuto (el servidor los averigua mientras se ve; preguntar solo «cerca del final» no vale: los créditos de una película pueden durar diez minutos), y la tarjeta sale **al empezar los créditos** o, si no se sabe, a 45 s del final (`momentoDeAviso`). Con siguiente episodio: un solo botón, «Siguiente episodio», que es la cuenta atrás (se va llenando y, al llenarse, se pulsa solo). **No hay botón de «Ver créditos»**, ni ahí ni en la pantalla del final: se pidió quitarlo porque todo esto existe para saltarlos (en la tele, Atrás cierra la tarjeta; en la web y el móvil, pulsar el vídeo encogido lo devuelve a pantalla completa). La decisión **`final`** (el vídeo **se encoge** y sigue con los créditos, y el resto de la pantalla ofrece «Más títulos como este», `/api/browse/relacionados`, con «Salir») es para una película o para **el último capítulo de la serie**, y nada más: `/api/next-up` devuelve `ultimo` (no existe ningún episodio después de este en disco ni en el catálogo, se pueda ver o no) y `decidir()` solo saca relacionados en una serie con `ultimo`. Antes salía en cualquier capítulo cuyo siguiente no se pudiera poner en ese momento (comprimido, ya visto, o si `/next-up` no reconocía el enlace), y con eso en mitad de las temporadas de «Tulsa King». **Un `ended` lejos del final no es el final** en ninguno de los tres reproductores (más de 15 s antes de la duración: el tramo de Telegram llegó corto): se vuelve a pedir ese punto. La tele no lo comprobaba, así que un corte a mitad de capítulo lo marcaba visto, sacaba la pantalla del final y, al volver, el vídeo «acabado» empezaba desde el principio. Antes, al acabar una película el reproductor se cerraba de golpe y devolvía a la portada. Cada cliente lo pinta a su manera (`FinTitulo.tsx`): la web, vídeo arriba a la izquierda y carátulas abajo, limitado también por el alto de la ventana o en una baja se pisaban; el móvil, vídeo arriba y rejilla de tres debajo; la tele, el mando es de esta pantalla en cuanto aparece (▲▼ botones o carátulas, ◀▶, OK) y el vídeo se encoge cambiando posición y tamaño, **sin transform**, porque en el Fire TV va en una capa que los ignora. En la tele la ficha la abre cada página con su estado y no una URL, así que el reproductor la pide con `tv/abrirTitulo.ts`, al que se apunta cada página que sabe abrir fichas. Ojo al probar el móvil en local: con el servidor de desarrollo el reproductor se cierra nada más abrirse, porque `StrictMode` lo monta dos veces y al desmontarse hace `history.back()`; en producción no pasa, así que se prueba con `vite build` + `vite preview`.
- **«¿Sigues ahí?»** (`useSiguiente`, el mismo en las tres apps; la pantalla es `components/SiguesAhi.tsx` en cada una). Con el cuarto capítulo seguido visto **sin tocar nada**, antes de empezar el quinto, en vez de saltar se pregunta, como Netflix: la cuenta son los saltos que hace la barra al llenarse sola (`SALTOS_SIN_PREGUNTAR` = 3), no se reinicia al cambiar de episodio y la pone a cero cualquier señal de que hay alguien —pulsar el botón de la tarjeta, una tecla o el mando, un clic o un toque, escuchados en el `document` (`mousedown` y no `pointerdown`, que Chromium 53 no tiene; mover el ratón no cuenta)—. Mientras pregunta el vídeo está en pausa, la tarjeta no vuelve a salir (`mirar()` sale antes) y, si el vídeo termina, el reproductor se queda abierto. Si la tarjeta iba a descargar algo («Ver 3x08 y descargar 3x09») no se descarga hasta que se contesta «Seguir viendo»; «Salir» cierra el reproductor. En la tele el mando es de la pregunta (◀ ▶, OK, Atrás sale) y en la PS4 se pulsa con el puntero.
- **El siguiente episodio: ver y descargar, en un solo botón**. Al final de un capítulo de una serie el reproductor pregunta, y lo que pregunta depende de lo que haya: si el siguiente **está en disco** sale la tarjeta «A continuación» con la barra que avanza sola y lo pone al llenarse (`CUENTA_ATRAS_S`, 15 s, desde 45 s antes del final: el salto cae sobre los créditos, como Netflix); si **no queda nada descargado** por delante, ofrece bajar **dos**; y si delante queda **solo uno**, ofrece ver ese y bajar **uno más**, que es lo que mantiene siempre un capítulo de reserva. Ese último caso **no son dos botones sino uno** («Ver 3x08 y descargar 3x09»): empezaron siendo dos y se pidió juntarlos, y es lo correcto, porque ahí nadie está eligiendo entre dos cosas, está diciendo «sigue». La barra es ese botón pulsándose solo, así que **el texto lleva escrito lo que va a pasar** —con los números de episodio— en vez de un «Siguiente» genérico: si la barra llega al final y arranca una descarga, tiene que haber estado dicho antes. Y por lo mismo la tarjeta de descargar a secas **no lleva barra**: lo único que puede pasar sin que nadie toque nada es seguir viendo. Lo escribe `textoDe()` en `useSiguiente`, y la acción única es `confirmar()`. La decisión la toma el servidor (`services/siguiente.py`) porque hay que cruzar cuatro cosas —lo que hay en disco, lo que esta cuenta ya vio (reproducido o marcado a mano), lo que está bajando ahora y lo que el catálogo tiene— y eso no puede vivir copiado en cuatro clientes. Cuatro cuidados: **nada se descarga solo**, lo único que pasa sin pulsar nada es *ver* (no gasta disco ni cuota); el episodio que se deja **se marca visto antes de cambiar**, porque la cuenta atrás salta sobre los créditos y el `ended` no va a llegar nunca; `POST /next-up/download` **recalcula** qué bajar en vez de fiarse del cliente, porque entre pintar la tarjeta y pulsarla puede haberlo bajado otro; y la descarga pasa por `iniciar_descarga()`, la misma función que el botón de la ficha, así que las comprobaciones de cuota y de duplicados son las de siempre. El reproductor cambia de episodio **él solo** (`actual` en su estado interno, no en las props): si no, habría que enseñar lo mismo a la ficha, la portada y Descargas de cada cliente.
- **El móvil ya no usa la pantalla completa del sistema, y es a propósito**. Antes, en cuanto arrancaba el vídeo se llamaba a `webkitEnterFullscreen()` y se le pasaba al reproductor de iOS, que trae más cosas hechas (girar a apaisado solo, su propio botón de salir). El problema es que ese reproductor **se pinta fuera de la página**: encima de él no se puede dibujar absolutamente nada, así que la tarjeta del siguiente episodio obligaba a salirse de la pantalla completa para poder verse. Se pidió que apareciera dentro del reproductor, sin tener que salir, igual que en la web y en la tele, y la única forma es no entrar. Ahora el `<video controls playsinline>` ocupa la pantalla **dentro de la página**: se ganan la tarjeta, el botón de cerrar y cualquier cosa que haya que pintar encima; se pierde el giro automático a apaisado, que es cosa del reproductor del sistema y no hay API para pedirlo sin él. El botón de pantalla completa de la barra nativa sigue estando: si alguien entra por ahí, la tarjeta al aparecer **se sale sola** (`porLaTarjeta`, que existe porque salir de la pantalla completa es también la señal del botón «Hecho»). Y como ya no hay «Hecho», el botón de cerrar lo pone ahora el propio reproductor. En la tele el problema es otro: mientras el capítulo corre, las flechas son el salto de 10 s y OK es la pausa, así que la tarjeta **no se queda con el mando** hasta que se entra a propósito (▼) o hasta que el vídeo termina (`sig.alFinal`).
- **Un `error` del `<video>` no es prueba de que el vídeo no se pueda ver**. El reproductor del móvil pintaba «No se ha podido abrir el vídeo. Puede que el archivo no esté listo todavía.» en una pantalla translúcida **encima de una película que se estaba reproduciendo perfectamente**, y sin forma de quitarla. La causa no es el archivo: el `<video>` se inserta en la página **antes de tener `src`** —la entrada de reproducción (`streamTicket`) es un viaje al servidor—, y un elemento de medios que entra en el documento sin fuente dispara un `error` él solo (el algoritmo de selección de recurso no encuentra candidato y pone `MEDIA_ERR_SRC_NOT_SUPPORTED`). El fallo era viejo y **estaba tapado**: mientras el móvil entraba en la pantalla completa del sistema, esa pantalla se pintaba en la página, o sea debajo, y no se veía; al pasar a reproducir dentro de la página quedó a la vista. Dos reglas de aquí en adelante. Un reproductor **no tiene pantalla de error**: lo que hay es la pantalla de carga, y si el archivo de verdad no abre lo dice el reproductor del sistema con su propio icono, que es la única señal que no puede equivocarse (en la tele el aviso es un toast de 5 s, y mira `v.error` antes de abrir la boca). Y la entrada de reproducción **está limitada a una ruta**, así que al cambiar de episodio se olvida (`setTicket(null)`) en vez de reaprovecharla: con la del capítulo anterior el servidor contesta 401 y el `<video>` suelta otro error que tampoco significa nada. Ojo al diagnosticar algo parecido: que esto saliera justo en las películas de otro usuario fue casualidad doble (ahí había un 404 real, el de `video_en()`), y buscar la causa en los permisos no llevaba a ninguna parte.
- **El reproductor del móvil se monta por portal en el `<body>`, y la barra de arriba se esconde sola**. Dos cosas que salieron en cuanto el vídeo dejó de irse a la pantalla completa del sistema. La barra de pestañas se pintaba **encima del vídeo** por mucho `z-index` que llevara el reproductor: `.app-main` lleva `-webkit-overflow-scrolling: touch`, que en iOS crea su propio contexto de apilado, y dentro de él un `position: fixed` deja de colocarse respecto a la ventana y su `z-index` solo compite con sus hermanos —así que la barra (z-40, hermana del `<main>`) ganaba siempre—. Ahora el reproductor vive en `.player-shell` montado por portal en el `<body>`, fuera de ese contexto; es el mismo motivo por el que la app de la tele monta sus paneles en `#overlays`. Y su alto es el medido (`--app-h`) y no `100%`, para que los controles nativos del vídeo, que se pintan al borde de abajo del elemento, no queden debajo de la barra de direcciones de Safari. Lo segundo: el botón de cerrar con el título **se quedaba puesto toda la película**. A iOS no se le puede preguntar si sus controles están visibles, así que la barra hace lo que hacen ellos —asoma al tocar la pantalla y se retira a los cuatro segundos—, que es lo que deja las dos cosas más o menos a la vez. Con la barra escondida un toque la devuelve, que es por donde se cierra.
- **Apple valida el `sub` de la firma VAPID**. Sin `TMD_PUSH_CONTACT` se firmaba con `mailto:admin@moviesandchill.local`, y Apple rechaza un contacto que no parezca real (403 `BadJwtToken`): los avisos no llegaban **nunca** al iPhone. Ahora, sin correo, el contacto es `TMD_PUBLIC_URL` (una https real). Encima el fallo se escondía solo: cada rechazo sumaba en `failures`, a los cinco se **borraba la suscripción** y el teléfono seguía diciendo «Avisos activados», porque eso lo dice el navegador y no el servidor. Por eso un 401/403 ya no cuenta como fallo del aparato (es de nuestra firma), los clientes vuelven a mandar su suscripción al entrar (`reafirmarAvisos()`, que además la pasa a la cuenta que haya entrado en ese aparato) y «Enviar uno de prueba» enseña lo que contestó Apple o Google. Cada aviso de descarga deja una línea en el log, llegue o no.
- **Al terminar una descarga se avisa a quien la pidió**. Va en el momento, desde el final de `_download_batch`, y no desde un vigilante periódico como los avisos de episodio nuevo: ahí ya se sabe todo (quién la pidió, qué título es, qué archivos han caído), mientras que cuando un archivo se indexa todavía no se sabe de qué serie es. El texto dice **el título**, no el nombre del fichero («Suits · 3x08», no `Suits.S03E08.1080p.WEB-DL.x264.mkv`), y para eso la ficha del catálogo se guarda en el lote al empezar y no se vuelve a consultar al acabar. Si el servicio de push falla se registra y se sigue: la descarga ya ha terminado bien y un aviso que no sale no puede convertir eso en un error. Un aviso de descarga sin ficha de TMDB lleva a **Descargas** y no a la portada (los dos service workers lo miran por `reason: "descarga"`).
- **Plataformas: se pregunta por cada título nuestro, no por lo último de cada plataforma**. Pedir a TMDB lo más nuevo de Netflix y buscarlo en el catálogo dejaba filas de tres tarjetas (lo recién estrenado casi nunca está aún en los canales). `services/plataformas.py` pregunta por cada título del catálogo (las series todas, las películas de los últimos cinco años) con la ficha y las plataformas en una sola consulta (`append_to_response=watch/providers`), cada semana, y guarda **todos** los proveedores de suscripción (`flatrate` y `ads`) en `tmdb_plataformas`: añadir una plataforma es tocar `PLATAFORMAS` y nada más. La columna `version` existe para eso: lo guardado con un formato anterior se vuelve a mirar sin esperar a que caduque. **Una serie es nueva por su última temporada** (`ultima_fecha` = el último episodio emitido), y eso vale también para «Novedades», que antes miraba el estreno y no dejaba entrar nunca la temporada nueva de una serie vieja; lo que ha llegado a una plataforma en los últimos 90 días pesa ×3 en su sorteo. **Hulu no está porque en España no existe**: sus series TMDB las da como Disney+. En el móvil la pestaña son dos píldoras encima de la portada y no una pestaña de la barra, que con seis ya no cabe.
- **Tops: Netflix es la única que publica el suyo**. Netflix deja cada semana, por país, sus diez películas y diez series más vistas en un TSV público (`all-weeks-countries.tsv` de Tudum): para Netflix se usa eso, con los títulos (vienen en inglés y sin id) emparejados en TMDB quedándose con el resultado que está en Netflix en España. Ese archivo cuenta **cada parte o temporada por separado** (la semana del 4 de noviembre de 2026 salió «Lupin: Part 1» a «Part 4», las cuatro entre las diez series), y dentro de la app de Netflix sale una vez: `juntar_partes()` deja una tarjeta por título en su mejor puesto («Partes 1 a 4») y sube a los de detrás; se aplica al sacar la foto y también al leerla, para que una foto ya guardada se vea bien. Probado en `backend/tests/prueba_tops.py`. Ninguna otra plataforma publica nada: su «Top 10» solo existe dentro de su app y con sesión. **FlixPatrol** lo recoge, pero su web (y su API interna) está detrás de una protección anti-bots de Cloudflare y no se va a sortear; su API oficial es de pago, y si algún día se contrata basta con cambiar la fuente en `tops.py`. Para el resto se usan **las tendencias de la semana de TMDB** filtradas por plataforma en España: se probó la popularidad a secas y no sirve, porque acumula y el top de Disney+ salía lleno de «Anatomía de Grey». Las plataformas pequeñas apenas salen en las tendencias mundiales, así que su lista se completa con lo más popular **reciente** de la propia plataforma (películas del último año, series estrenadas en los dos últimos), y un top de menos de 5 no se enseña. **Entra lo que no tenemos**, con «Pedir» (ver peticiones): es el top de verdad, no «lo mejor de lo nuestro». La foto se saca una vez al día (`fotografo` mira cada hora si la de hoy está), y `/browse/plataformas` es personal desde entonces, porque cada tarjeta dice si esa cuenta ya la ha pedido. Las filas de Plataformas van **aplanadas** con `seccion` (plataforma y logo de TMDB) y `titulo`, para que el motor de carriles de web y móvil sirva sin cambios; `genre` lleva la plataforma delante porque es la clave única de cada carril.
- **Peticiones: el mensaje sale de la cuenta de Telegram del servidor**, o sea de la del admin, aunque lo pida cualquiera. Por eso: límite de `LIMITE_DIA` (3) al día por cuenta salvo el admin, **nada se manda dos veces** (quien pide algo ya pedido, en cola o enviado, se suma a la espera, sin escribir nada y sin gastar límite), y **todo pasa por una cola** que sale de una en una, como mucho **una a la hora** en total (`MINUTOS_ENTRE_ENVIOS`): pedir solo encola (estado `en_cola`, con `orden`) y el vigilante mira cada minuto si toca mandar la primera. Cuánto falta lo calcula **Postgres** (`segundos_para_siguiente`, desde el último `intento_en`): comparar con la hora del contenedor mezclaría zonas. El admin la maneja en Admin → Peticiones (subir, bajar, primera, «Enviar ya» —cuenta como el envío de esa hora—, quitar → `descartada`, y «Volver a la cola» para una fallida o descartada). La publicación se puede **pausar** desde ese mismo bloque (`peticiones_pausadas` en `app_settings`): se sigue pidiendo y la cola se llena, pero el despachador no manda nada hasta reanudar; «Enviar ya» sí funciona, porque es una orden explícita del admin, y los clientes dicen «en pausa» en vez de una hora estimada. Una que Telegram rechaza queda `fallida` con el motivo y **no se reintenta sola** (contra un chat que no deja escribir no arregla nada). Lo que llega mientras espera en la cola se da por conseguido **sin mandarse**. Con más de `AVISO_COLA` (5) en cola, aviso push a los admins **una vez cada vez que se cruza el umbral** (`peticiones_aviso_cola` en `app_settings`), con `reason: 'peticiones'`, que los service workers abren en Admin → Peticiones. El chat lo elige el admin en **Admin → Peticiones** entre todos los de la cuenta (`iter_dialogs`), por defecto solo **los del catálogo y sus grupos de conversación** (el `linked_chat_id` de cada canal: un canal de difusión no deja escribir a nadie, las peticiones van en su grupo), y solo los que dejan escribir. Si el grupo es un **foro** (`forum`), se elige además el **tema** (`messages.GetForumTopicsRequest`; en Telethon 1.45 no está en `channels`) y el mensaje se manda con `reply_to=<id del tema>`, que es como Telegram publica en un tema; en «General» (el 1) va sin `reply_to`. «Enviarme una prueba» manda el ejemplo, carátula incluida, a los **Mensajes guardados** de la cuenta, para ver cómo queda sin escribir en el grupo. La plantilla se rellena a mano (`rellenar()`) y no con `format()`, para que unas llaves de más no tumben el envío. Con carátula, el mensaje sale como **foto con el texto de pie** (a 500 px; el pie admite 1.024 caracteres); si Telegram no acepta la imagen, se manda el texto solo: la petición no se pierde por la foto. Si Telegram falla la petición queda `fallida` **sin nadie esperando** y el siguiente que la pida la reintenta. «Ha llegado» es que haya un archivo con ficha válida (`tmdb_valid`); lo mira un vigilante cada 5 minutos porque al indexar todavía no se sabe de qué título es. En los clientes TMDB solo se consulta al pulsar «Pedir «lo buscado»» (botón si el catálogo no encuentra nada, enlace al final si sí), nunca por tecla. Probado en `backend/tests/prueba_peticiones.py`.
- **Lo que llega en vivo se compara con lo pedido** (`buscar_peticion.contra_peticiones`, desde `index_live_message`, justo después de indexar y antes del bucle de TMDB). Antes una petición se recogía solo cuando el bucle de TMDB le ponía al archivo **la misma** ficha, y eso falla con lo que más se pide: un estreno con el mismo título que otra película acababa con la otra y la petición seguía esperando con su mensaje en el grupo. Como la ficha de lo pedido se sabe de antemano, se compara con `veredicto()` (lo mismo que la búsqueda de antes de pedir: mismo título en español o el original —`peticiones.titulo_original`, que las antiguas piden a TMDB una vez—, año ±1, tipo, nada de extras), lo que es ese título se indexa con esa ficha y `tmdb_manual`, y `repasar()` la recoge en segundo plano (aviso y borrado del mensaje; va con un candado, `_repaso`, porque también la lanza el vigilante). Sin peticiones activas no cuesta más que una consulta. **`update_media_tmdb_many` ya no pisa una ficha `tmdb_manual`**: el bucle de TMDB podía coger el archivo entre que se indexa y se empareja con la petición (protege también las correcciones de Revisión). Solo cubre lo que llega en vivo; lo que entra por un barrido lo sigue recogiendo el vigilante por su ficha. Probado en `backend/tests/prueba_buscar_peticion.py`.
- **Al conseguirse una petición, su mensaje se borra del grupo** (`peticiones.borrar_mensajes`, al final de cada `repasar()`): uno ya conseguido que sigue ahí parece pendiente para quien lee el grupo. Se borra para todos (`revoke=True`; una cuenta puede borrar sus propios mensajes de un grupo sin límite de tiempo) y queda en `peticiones.mensaje_borrado`: `NULL` pendiente, `si`, `no: <motivo>` (Telegram dijo que no: no se insiste) o `antes` (conseguida antes de que esto existiera: al crear la columna se marcaron así y no se tocan). Sin conexión con Telegram se queda pendiente para la siguiente pasada. Lo que se consiguió sin llegar a escribirse (estaba en la cola, o se encontró en los canales al pedir) no tiene mensaje. Volver a mandar una petición pone la marca a `NULL`. El panel de Peticiones lo dice en cada conseguida. Probado en `backend/tests/prueba_peticiones.py`.
- **Antes de pedir, se busca en los canales** (`services/buscar_peticion.py`): al pedir y otra vez justo antes de mandarla (una petición puede pasar horas en la cola). Muchas peticiones eran de cosas ya publicadas que el catálogo no tenía emparejadas (sin ficha, con otra) o ni indexadas. Se busca con el **título tal cual**, en español y en el original, quitando solo un año entre paréntesis (Telegram busca por palabras y un «2024» que el archivo no lleve lo dejaría fuera; «1917» o «Blade Runner 2049» se quedan): primero en el catálogo, lo que no tiene ficha válida ni está corregido a mano (lo bien emparejado con otro título no se toca), y después con la búsqueda de cada canal, lo no indexado, por el nombre del archivo **o por el pie** (en un grupo con temas la búsqueda los recorre todos, también los que no se indexan: lo de un tema ignorado se descarta). Cada candidato se compara con la ficha de TMDB de la petición (`veredicto`): **el mismo título, no parecido** (las mismas palabras normalizadas: «Dune» no es «Dune: Parte dos», y las secuelas son justo lo que se confunde), el año si alguien lo dice (±1, por los estrenos en España), el tipo (un capítulo no es la película), y si la ficha del canal enlaza a TMDB —o el nombre lleva `[tmdbid-N]`— manda eso; una película sin año en ningún sitio solo vale si la ficha del canal la respalda (un remake tiene el mismo título). Los extras, *making of*, tráileres y muestras no cuentan nunca (cuelgan de la misma ficha que la película: pasó con «Extra - Aliados.7z.001»), y si el nombre del archivo dice un título parecido pero distinto («Aliados 2», «Nuestros maravillosos aliados») manda el nombre y no la ficha de encima. **La búsqueda de Telegram no mira dentro de nombres con puntos**: «Aliados.part1.rar» no sale buscando «Aliados» (sí lo que lo dice en el pie o lleva espacios); lo indexado se encuentra igual porque eso se busca en el catálogo, normalizado. La ficha del canal sale del pie o, si no dice nada, del último de los seis mensajes de antes que diga un año o enlace a TMDB, y solo se pregunta si hace falta. Lo que pasa se indexa con esa ficha y `tmdb_manual` (como una corrección de Revisión: nada automático la cambia) y la petición queda **pedida y conseguida** sin escribir en ningún grupo y **sin gastar del límite del día**; si se encuentra mientras espera en la cola, `repasar()` avisa a quien la esperaba. La búsqueda tiene 25 s (`ESPERA_S`): si Telegram tarda o falla, se pide como siempre. Cada candidato deja una línea en el log con el sí o el no y por qué. Probado en `backend/tests/prueba_buscar_peticion.py`.
- **El nombre del archivo es lo peor que hay para saber qué película es; el canal lo dice mejor**. En YoSoyFran (y en muchos canales) cada película es un bloque: una **foto de ficha** («LA SILLA (2026) · Estreno… · Géneros…», a veces con enlace a TMDB/IMDb o la carátula de `image.tmdb.org`), debajo uno o varios **archivos con su pie** («🎬 LA SILLA 💎 TERROR 🍿 2.026», «El Experimento | The Experiment (2010)») y una **pegatina** que cierra el bloque. Antes solo se leía el nombre, y solo el 32 % de las «películas» tenía carátula. `services/contexto.py`: `Seguidor` ve **todos** los mensajes en orden (el escaneo y el vivo van del más viejo al más nuevo) y a cada archivo le pega la última ficha **de su mismo tema** (en un foro los temas se intercalan), **mientras el tema siga publicando sin pausas de más de 5 minutos** (`VIGENCIA`; eran 90 minutos contados desde la ficha, y en los temas de series una cabecera de hacía una hora se pegaba a la tanda siguiente: «Ninja Hattori S01E001» con la del Coyote y el Correcaminos) y sin pegatina en medio; `pistas_de()` saca título, año, título original y enlaces de un texto. Se guarda en `media_items` (`pie`, `ficha`, `tema_id`, `pistas`). Al enriquecer, el orden es: enlace a TMDB/IMDb (`/find` para IMDb, y entonces el tipo del enlace manda sobre el del nombre), título y año de la ficha o el pie, título original, y solo al final el nombre del archivo. Sin ficha de TMDB, el buscador enseña título, año, carátula y sinopsis de la ficha del canal (`de_ficha`). Al releer, **todo** (menos lo corregido a mano) se vuelve a buscar en TMDB con las pistas nuevas, también lo que ya tenía ficha y carátula, porque había errores con carátula (la otra «Animales» de 2026). Para no vaciar la portada mientras dura, la ficha que tenía **se queda** (solo se marca `tmdb_searched = FALSE`, y `get_media_without_tmdb` coge también esas, después de lo que no tiene ficha): si se encuentra otra se cambia y el log lo dice (`CAMBIA N (antes tipo/id)`), si no se encuentra nada se queda la de antes, y un resultado del tipo equivocado no sustituye a una ficha buena. Lo indexado antes de esto lo **relee** `services/relectura.py` (una vez, en segundo plano y con pausas; lo releído queda en `contexto_leido`, así que tras un reinicio sigue sola donde iba. **No** se apunta un «voy por el mensaje N» para empezar por ahí: se probó y se saltaba lo pendiente de antes de ese punto, que acababa dado por borrado. Se empieza siempre un poco antes del primer pendiente. Lo pendiente cuyo mensaje ya no está en Telegram se da por leído, o cada vuelta recorrería el canal entero. Solo corre si hay pendientes: lo que se indexa entra ya con su contexto, así que solo aparecen al arrancar —por un cambio de `contexto.VERSION` o por restos que no se pudieron leer—; al arrancar se cuentan y, con cero, no hace nada hasta el siguiente arranque, y si quedan restos se reintenta cada 6 h hasta dejarlo a cero. Se ve en Admin → Canales, con «Releer ahora»): le pone el contexto, de paso lo vuelve a pasar por el limpiador actual, y lo que no estaba bien emparejado vuelve a buscarse en TMDB; lo bien emparejado no se toca. Para ver cómo publica un canal: `GET /api/admin/telegram/mensajes?channel_id=…&tema=…` (solo lectura) y `/temas`. **Cada canal lo escribe a su manera** y las cuatro formas que hay se leen: YoSoyFran («LA SILLA (2026)» y pies con emojis), K9 (una ficha por campos, «Nombre: King Kong / Año: 1933 / Director: …», y el original entre paréntesis: «Zombi (Dawn of the Dead)»), Las Cositas 3 (la calidad entre paréntesis y sin año: «Buddy (1080p) / SINOPSIS: …», «Cyberpunk: Edgerunners - Temporada 2 (1080p)») y Las Cositas Ballin, que es un tema de **conversación** donde la gente sube cosas («VECINOS INVASORES Audios en Castellano…», «Gen V (Spin off de The Boys) mkv y zip»). Por esto último una ficha solo se pega al archivo si **comparten alguna palabra** (`concuerda()`; una que empiece como la otra también vale: «Gen V» y «Generación V 1x01»): en una conversación la foto de uno y el archivo de otro pueden ir seguidos. Un archivo cuyo nombre no dice nada se lleva la ficha que tenga encima. Al cambiar cómo se leen las fichas hay que subir `contexto.VERSION`: la relectura vuelve a pasar entonces por todo lo ya releído (`olvidar_contexto()`), porque lo guardado se sacó con las reglas viejas.
- **Casi todas las «películas» sin carátula eran capítulos**. De las 5.198 de YoSoyFran sin ficha, 4.800 estaban en los temas «Series» y «Dibujos»: capítulos que el nombre del archivo no decía que lo eran. Lo decide ahora `contexto.interpretar()` y no `parse_filename()` a secas, en todos los sitios donde se decide qué es un archivo (escaneo, vivo, relectura, enriquecimiento y «Reclasificar»), con lo que se sabe de él: **el pie** dice el capítulo aunque el archivo no («60b016c396c7.mp4» con el pie «La reina del flow 2x23»); y **un capítulo con nombre de capítulo** («12 - Televisatron», «063 ¡Resonancia!…», «Fraguel_Rock_63», `numero_suelto()`) es de la serie que nombra la **cabecera de su tanda** («LOS IMPOSIBLES», «Saint Seiya Saga Las 12 Casas. Capítulos 041-073») si el **tema del foro es de series** (`tipo_de_tema()`: «Series», «Dibujos…»; «Películas y Series» no dice nada) o la cabecera dice que es una serie («Capítulos», «Temporada», «S3»). Nunca con año en el nombre: «10 vidas (2024)» es una película de dibujos aunque empiece por un número y esté en «Dibujos». En un tema de series la cabecera vale aunque no comparta palabras con el capítulo, y una línea de texto suelta sin año («Fragguel Rock») también es cabecera. Los tipos de cada tema se preguntan a Telegram una vez por hora y canal (`tipos_de_temas()`). El limpiador entiende además «T6 C07», «S0107» (solo temporadas 01-19: «Honda S2000» no es la 20), «Capítulo 1229» y «AÑO 2.025». Medido sobre el catálogo: 3.220 «películas» sin ficha pasan a capítulo, y 1.667 capítulos que estaban emparejados con una *película* de TMDB («Futurama T11 C05», «Prison Break T3 C10») se vuelven a buscar como serie; ninguna serie pasa a película. En TMDB, entre varios resultados con el mismo título y año gana el más votado (había dos «Animales» de 2026 y se cogía la que no era, así que la del top de Netflix seguía «por pedir»), se prueban también los títulos del pie (`Pistas.otros`), los números romanos en cifras («Solo en Casa IV» → «Solo en casa 4») y sin el número de orden de una saga («07 - James Bond - …»). Y en las fichas: una etiqueta con un emoji delante («🎬 Nombre:», «▪️ Titulo:»), las etiquetas `#` de Telegram, una sinopsis en la primera línea (más de diez palabras no es un título) y el título original en la segunda línea («🎬 Animales (2026) / Animals»).
- **Las fichas «enriquecidas» no traen texto**. Telegram tiene un formato de mensaje nuevo, como una página (carrusel de fotos, titular, sinopsis desplegable, tablas), que llega en `msg.rich_message` con `msg.message` **vacío**: así son ya muchas fichas de YoSoyFran (26 de los últimos 1.500 mensajes de «Películas», las más recientes) y la de «Animales» salía en blanco. `contexto.texto_de()` lo aplana (`_texto_rico`: un bloque por línea, enlaces incluidos) y el seguidor lo toma por cabecera. Telethon 1.45 ya lo recibe; lo que faltaba era leerlo.
- **Cuándo la ficha de encima es la de un archivo** (`Seguidor._le_toca`), medido contra Telegram en cinco temas de tres canales: si comparten palabra (`concuerda()`: parecidas, siglas como «HDA», o abreviaturas que quitan letras como «LyOuve» = «Ley y orden UVE», «FLX» = «Félix el gato»), si el nombre no dice nada («output.mp4»), o si es un capítulo que solo dice su número en un tema de series («12 - Televisatron»). Un capítulo que **dice su serie** («Ninja Hattori S01E001») tiene que ser de la de la cabecera. Y una película con el nombre en otro idioma («Your Fault_ London» bajo «Culpa tuya: Londres (2026)») vale solo si la cabecera es una ficha de verdad (`_parece_ficha`: año o campos como «Género:», «Sinopsis»), **la subió el mismo** que el archivo (en Las Cositas Ballin, que es un tema de conversación, la foto de uno y los archivos de otro van seguidos) y el bloque es de una sola cosa. Una cabecera también puede ser un texto con campos de ficha sin año («🎬 Nombre: Rock of Ages / 🎭 Género/s: …»). Se probó a montar bloques explícitos (cabecera + archivos + enlaces a menos de 5 min) y no mejoraba esto: los mensajes de solo enlaces casi no existen (4 en 800 de Las Cositas Ballin: YouTube, Google Docs, Mega) y la cabecera **después** de los archivos solo apareció en «Los Simpson — FINALIZADO», cuyos archivos ya dicen la serie. El prototipo y la sesión de prueba (`session/prueba_local.session`, aparte de la del servidor: **nunca** usar la misma clave desde dos sitios, Telegram puede cerrarla) quedaron fuera del repo.
- **Lo mal indexado se ve en Admin → Revisión** (`services/revision.py`), en cuatro motivos: **sin ficha**, **tipo cruzado** (la ficha es de serie y el archivo parece película, o al revés: no sale en la portada), **ficha dudosa** (el canal dice un título, por su ficha o su pie, y la de TMDB es de otro o de otro año; solo en películas, porque en una serie la pista es el pie del capítulo) y **sin carátula**. Va **agrupado por lo que es**, no archivo por archivo: el título que dice el canal o el nombre de la serie, así que 200 capítulos sin ficha son una fila. Corregir un grupo le pone la ficha elegida a todos sus archivos (los capítulos, con su temporada y su número) y los marca **`tmdb_manual`**: la relectura no les cambia el tipo ni la ficha y «Reclasificar» se los salta. «Ignorar» los marca igual sin ficha, para lo que no es nada (avisos del canal, vídeos de prueba). Calcularlo cuesta ~10 s (se interpreta cada archivo con su contexto), así que se guarda en memoria cinco minutos y se olvida al corregir. Para elegir la ficha se reutiliza `GET /api/peticiones/buscar`. Lo que **no** detecta: un homónimo con el mismo título y año («Animales» de 2026), que se elige ahora por votos y, si la ficha lo dice («En streaming: Netflix»), por la plataforma (`tmdb.en_plataforma`).
- **La revisión automática** (`services/revision_auto.py`) hace sola lo que antes era a mano grupo a grupo. Medido en noviembre de 2026 (6.431 grupos, 15.112 archivos), casi todo eran **series tomadas por películas** (Black Clover, Minky Momo, Código Lyoko: decenas de archivos numerados que se buscaron en TMDB como película y se quedaron con una de título parecido) y **coincidencias exactas que se quedaron en «dudosa»**. Para cada grupo deduce el tipo **por sus archivos** (`tipo_y_episodios`: con capítulos numerados es serie, diga lo que diga el nombre), busca con `tmdb.exactos()` (título u original exactamente iguales) y decide con `decidir()`: **segura** se aplica sola —una sola coincidencia exacta con carátula y, en película, el año del canal cuadra; en serie, **todos** los archivos tienen su capítulo—; si el tipo se ha dado la vuelta por los números y existe también una película que se llama así («Star Wars» 4, 5 y 6), no. Lo demás queda como **sugerencia** en el panel («Sí, es esta» / «No es esta»). Lo aplicado guarda cómo estaba cada archivo (`antes`) y sale en «Corregido solo» con **Deshacer**; lo deshecho o descartado no se vuelve a aplicar ni a sugerir. Va **según entra**: cada 15 min mira una huella del catálogo (último id, archivos ya buscados en TMDB y corregidos a mano) y, si ha cambiado, primero la pasada exacta sobre los grupos nuevos y después un lote para Claude con lo que quede; al acabar un lote manda el siguiente si ha entrado más. Lo que se quedó sin coincidencia se repasa cada 6 h. También con «Revisar ahora». El capítulo de cada archivo lo saca `revision.capitulo_de()`, más permisivo que el parser («1 x 7», «S1.03», «T03, E05», «C07», «(12)», «#05», «Cap_101» o un único número suelto) porque solo se usa con el grupo ya reconocido como serie; con dos números («Medabots 2 54») no adivina. De paso, «Corregir» a mano ya pone los capítulos al pasar un grupo de película a serie: antes se quedaban sin número de episodio. **Los capítulos cuyo nombre no dice de qué serie son** («Capítulo 1639», «S10E009», «12x01. Quien lo encuentre…» bajo una cabecera «Temporada-12ª») se agrupan **por canal y tema** y no por título: por título cada uno era su propio grupo (unos 1.700 de un archivo, una telenovela de 2.000 capítulos uno por uno). Medido, cada uno de esos temas era de una sola serie; aun así nunca se aplican solos, en la lista llevan cuatro archivos de muestra (`ejemplos`) y el buscador de «Corregir» llega vacío (`busqueda`). Probado sin TMDB en `backend/tests/prueba_revision_auto.py`. **Lo que la revisión exacta no resuelve lo decide Claude** (`services/revision_ia.py`, apagado hasta poner la clave de Anthropic en `TMD_ANTHROPIC_API_KEY` y encenderla en Admin → Revisión): a cada grupo pendiente (sugerencia o sin coincidencia exacta; los capítulos sin nombre de serie van por la búsqueda de abajo) se le buscan hasta 10 candidatas en TMDB, por el título, el original y **sin el número de capítulo** (`revision_auto.sin_capitulo`: «Black Clover 151» → «Black Clover», «DBZ Kai 36 Cast Cat Gal Eusk» → «DBZ Kai»; buscando el título tal cual, dos de cada tres «sin ficha» se quedaban sin ninguna candidata y no llegaban a Claude) y se manda a **Claude Haiku 5.5** con lo que dice el canal (**Haiku hace el trabajo y Sonnet 5.5 solo verifica**: lo que Haiku elige queda como propuesta —`ia = por_verificar`, en la columna `propuesta`— y el lote siguiente es de Sonnet, que recibe el grupo y esa ficha y dice si es correcta; solo se aplica sola lo que **Sonnet confirma con seguridad alta**, lo que confirma con dudas queda como sugerencia y lo que rechaza se queda a mano con lo que propuso Haiku y por qué no. En la búsqueda en TMDB igual: busca Haiku y verifica Sonnet en el momento. Haiku cuesta 20 veces menos y lo que da por «ninguna» no le cuesta nada a Sonnet; medido sobre 20 grupos reales, 1,6 céntimos en total frente a los ~15 que costaba Sonnet solo, con 5 aplicadas, 1 sugerencia, 2 rechazadas por Sonnet —un capítulo con la ficha de la película, «iCarly» habiendo un remake— y 7 «ninguna». Las marcas de cuando decidía Sonnet solo, `claude-sonnet-5-5` y `claude-sonnet-5-5+tmdb`, se siguen entendiendo); Claude **solo puede elegir entre esas candidatas** (sus claves van como lista cerrada en el esquema de la respuesta) o «ninguna», con seguridad y motivo. Seguridad alta y las comprobaciones de siempre (carátula; en serie, todos los capítulos) → se aplica sola con su `antes`, sale en «Corregido solo» y **desaparece de la lista en el momento** (`revision.quitar`, sin recalcularla; el panel vuelve a pedir la lista cuando cambian las cifras, y sin nada en marcha mira cada minuto); si no, sugerencia con la razón de Claude. Al principio decidía Sonnet solo; se eligió midiendo antes: 35 grupos reales cuyo canal enlaza la ficha (con el enlace borrado, 23 ambiguos, 11 sin la buena entre las candidatas) y Haiku 5.5, Sonnet 5.5 y Opus 5.5 acertaron los 35 sin ningún error con seguridad alta; Haiku se atrevía con menos y Opus costaba el doble sin aportar nada. Va por la **Batch API** (la mitad; el lote en marcha se apunta en `app_settings.revision_ia_lote` y se mira cada 5 min, así que sobrevive a un reinicio) con **tope de gasto mensual** (`revision_ia_tope`, 20 $ por defecto; el gasto real sale del `usage` de cada respuesta). **Preparar un lote tarda minutos** (las candidatas de cada grupo se buscan en TMDB), así que «Mandar» contesta al momento y lo prepara en segundo plano (`preparando` en el estado, con su progreso), con **un solo lote a la vez** (`_cerrojo_mandar`) y el lote **apuntado nada más crearse, protegido de cancelaciones** (`asyncio.shield`). Pasó el primer día: esperando la respuesta, el navegador cortó la petición, el servidor abandonó el trabajo justo después de crear el lote en Anthropic y antes de apuntarlo, y quedó un lote huérfano (cobrado y sin recoger) con el botón otra vez disponible para mandar los mismos grupos. **Lo que de verdad pasó ese día fue otra cosa, y costó 8,94 $**: al apuntar el lote, `json.dumps` de las candidatas fallaba con «Object of type date is not JSON serializable» (TMDB trae la fecha de estreno como `date`), así que el lote quedaba cobrado en Anthropic sin sus grupos vinculados; al recogerlo no se reconocía ninguno, se apuntaba a 0 $ y se volvían a mandar los mismos (cinco veces en una hora). Tres arreglos: `default=str`; `recoger` da por suyos también los grupos que siguen esperando a Claude sin lote y apunta el coste de **todas** las respuestas, sean de un grupo que se aplica o no; y **`conciliar()`**, en cada vuelta del bucle, pide a Anthropic la lista de lotes de la cuenta (con la clave normal) y apunta lo cobrado por los que aquí no constan o constan a 0 $. El panel enseña además una **barra de progreso** de cada cosa en marcha (la pasada exacta, preparar el lote, el lote en Claude —`lote_progreso`, de los `request_counts` de Anthropic, preguntado como mucho cada minuto— y la búsqueda en TMDB). Un lote así se puede **adoptar** (`POST /api/admin/revision/ia/adoptar` con su id, `revision_ia.adoptar`): solo uno terminado y con al menos un 90 % de sus grupos (`r<id>`) esperando todavía a Claude; como no tiene las candidatas guardadas, la ficha elegida se pide a TMDB al recogerlo, con las mismas comprobaciones. No se adoptan solos a propósito: en la misma clave puede haber lotes de prueba cuyos `r<id>` coinciden por casualidad con grupos reales. **Lo que no se resuelve con candidatas lo busca Claude en TMDB él mismo** (`investigar_pendientes`, con la herramienta `buscar_tmdb`, hasta 6 búsquedas por grupo, a precio normal porque es un ida y vuelta que la Batch API no admite; por tandas de 150 en segundo plano). Le llega todo lo que el algoritmo no sabe (`situacion_de`, y el mensaje le dice por qué): «Sin carátula», lo que se quedó **sin candidatas**, lo que el lote contestó **«ninguna»** y los **capítulos sin nombre de serie** (estos solo como sugerencia, nunca se aplican solos). No le llega lo que no tiene nada que buscar («Capítulo 1840» con un `chunklist_….mp4`, «1x11»): medido, Claude dice «ninguna» y cuesta igual. Cada grupo se busca una vez (`ia = claude-sonnet-5-5+tmdb`). Medido sobre 23 grupos reales de los que antes no llegaban: 3 se aplicarían solos (Black Clover 150, Good Boy, Arirang), 7 quedan como sugerencia (Pretty Cure, Los sábados secretos, Los Simpson por el título de un capítulo) y 13 «ninguna», a unos 0,9 céntimos por grupo. En «Sin carátula» casi siempre la ficha sin imagen es otra entrada (una «Collection», un spin-off, una vacía) y las candidatas fijas no la encuentran: medido sobre 4 grupos reales, encontró Gomorra (2014) para «Gomorrah Collection», Física o química para «FoQ» y Marvel - The Punisher para una entrada vacía, con seguridad alta y entre 0,45 y 1,1 céntimos por grupo. Solo puede quedarse con una ficha que haya salido en sus búsquedas (`aplicar_eleccion` lo comprueba), y si elige la misma ficha sin carátula que ya tenía el grupo queda a mano. Ojo: los nombres de los campos de una herramienta no admiten «ñ» (400: `anio`, no `año`). En el historial sale como «búsqueda en TMDB». **El respaldo de otro modelo (`fallbacks`) no se puede usar: la Batch API lo rechaza con un 400**; un grupo que Sonnet rechace se queda a mano. **La clave va en el `.env` (`TMD_ANTHROPIC_API_KEY`) y no en el panel**: es un secreto y no tiene que poder leerse ni cambiarse desde la web; en el panel solo están el interruptor y el tope. Al encenderla se comprueba contra la API (`models.retrieve`, gratis), y si Anthropic la rechaza al mandar un lote (revocada, sin saldo) el motivo queda en `revision_ia_error` y sale en el panel. **Para seguirlo**: cada lote queda en la tabla `revision_ia_lotes` (grupos, aplicadas, sugeridas, ninguna, fallos, tokens y lo que costó de verdad), y el panel enseña el gasto del mes con una barra frente al tope, el gasto por mes y el total, los últimos lotes, y en «Corregido solo» un filtro «Lo que decidió Claude» con su marca. El tope se comprueba **antes** de mandar con una estimación con un 50 % de margen (`COSTE_GRUPO_ESTIMADO`), así que un lote no se pasa por calcular de menos. Al pasar del 80 % del tope y al alcanzarlo llega un aviso al móvil de los admins (`avisar_gasto`, cada uno una vez al mes, `reason: "revision"`, que abre Admin → Revisión).
- **Temas que no son de cine**. Un grupo con foro mezcla «Películas» y «Series» con «Deportes», «Todo Motor», «Libros», «APKs»… y todo eso se indexaba como películas (carreras de MotoGP, grabaciones con nombre de fecha). En Admin → Canales, por canal, se eligen los temas que **no** se indexan (`channels.temas_ignorados`): el escaneo y el vivo se los saltan (en Novedades sale «tema ignorado»), lo ya indexado de esos temas sale del catálogo, y si un tema deja de ignorarse se vuelve a indexar solo ese tema (`reindexar_temas`). El tema de los archivos antiguos se conoce cuando la relectura pasa por ellos.
- **El limpiador de nombres corta las películas en el año**: el título es lo de antes del primer año creíble (1900-2035) que tenga algo delante, entre paréntesis o suelto y aunque vaya pegado a una palabra («La_voz_dormida_2011DRAMA_…»). Quita además `ª`, `º` y emojis («La silla (2026) ª[HD]» mandaba «La silla ª» a TMDB), trata los puntos como espacios en nombres de «escena» sin espacios («Billy.Bathgate.1991…») y reconoce episodios de una cifra («1x5», que antes se tomaba por película). Medido sobre 20.000 títulos bien emparejados: solo 6 cambian de tipo, y los 6 eran episodios mal emparejados con películas. Probado en `backend/tests/prueba_title_parser.py`.
